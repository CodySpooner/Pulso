## What was built

- **API** `GET /v1/products` (`apps/api/src/pulso_api/routers/products.py`):
  - **New filters:** `store` and `supplier` (an id, 1 to 2^63 − 1, else 422).
  - **What matches:** a product with a live (not delisted) listing at that store or from that supplier.
  - **Shared check:** one `EXISTS` shape now serves `source`, `store` and `supplier`.
  - **Combining:** they AND with every other filter and keep the keyset cursor.
  - **Names for the chips:** `DiscoverPage` gains `store` and `supplier`. Each is `{id, name}` (a store's domain, a supplier's name) or null.
  - **Unknown id:** it lists nothing and its echo is null, as an unknown `category` or `source` already does.
- **Discover** (`url-state.ts`, `discover.tsx`):
  - `?store=<id>` and `?supplier=<id>` live in the URL like every other filter. Ids parse as safe positive integers, and anything else falls back to the default.
  - Each shows as a removable chip: icon, muted "Store" or "Supplier", the name in medium weight, then ×. The chip row sits in the toolbar's wrap under the filters at every width, outside the phone's filter sheet.
  - Chips count in "Filters (n)", and the sheet's "Clear filters" clears them too.
  - **Chip states:**
    - loading: a skeleton name, with "loading" for screen readers;
    - unknown id: "#id, not found";
    - feed error: "#id";
    - the filtered empty state names the vendor in its Remove button.
  - **Focus:** removing a chip focuses the other chip's ×, else the page h1, as after a navigation. Focus is never lost to the body.
  - **Motion:** chips leave with Motion pattern 5 (`layout` + `AnimatePresence`, scale 0.9 + fade, `spring.smooth`). Layout reflows only when a chip leaves (`layoutDependency`), so a name loading never projects a resize. Reduced motion fades without the scale.
- **Palette** (`command-palette.tsx`):
  - A store row opens `/discover?store=<id>`, and a supplier row opens `?supplier=<id>`, instead of the top product.
  - The footer reads "Show products". The screen-reader hint reads "(lists its products)".
  - Rows whose vendor has no live product stay disabled with "No products yet" (DEC-300 d).
  - Opened from Discover itself, the palette returns focus to where it was, since the route doesn't remount.

## Click count

Palette store row → Discover filtered by that store:
- **From an open palette: 1 click** on the row.
- **Keyboard: 0 clicks** (Ctrl+K, type, Enter).
- **Mouse from any page: 2 clicks** (the top-bar search trigger, then the row).
- **Phone: 2 taps** (the bottom bar's Search, then the row).

Removing the filter takes **1 click** on the chip's ×, or Enter on it.

## EXPLAIN: is an index needed? No

I seeded p2-16's realistic catalog (`test_search.py`'s `SEED`) in a temporary test, deleted before commit:
- 10,000 products and 30,000 listings (two store listings and one supplier listing each);
- 2,000 stores and 500 suppliers;
- then `VACUUM ANALYZE`.

I captured the feed query with `before_cursor_execute` and ran it under `EXPLAIN (ANALYZE, BUFFERS)`.

| Query | Items | Feed query execution | Plan for the filter | Request p50 / p95 (20 warm) |
|---|---|---|---|---|
| unfiltered | 48 | 158.0 ms | (DEC-041 aggregate sort over all products) | 118.5 / 277.6 ms |
| `store=1234` | 5 | **0.185 ms** | Bitmap Index Scan on `ix_listings_store_id` → HashAggregate (semi-join) → `pk_products` | 39.1 / 64.9 ms |
| `supplier=321` | 20 | **0.557 ms** | Bitmap Index Scan on `ix_listings_supplier_id` → the same | 32.3 / 158.9 ms |
| `store=1234&sort=newest` | 5 | 0.215 ms | as for the store | 33.1 / 38.0 ms |
| `supplier=321&sort=fewest_sellers` | 20 | 0.421 ms | as for the supplier | 30.9 / 36.3 ms |
| `store=999999` (unknown) | 0 | 0.099 ms | as for the store, no rows | 31.3 / 131.3 ms |

- **What the plan does:** the planner starts from the vendor's listings through the existing single-column indexes and never seq-scans `products`. Request time is the page's other queries (sources, degraded, margins), not the filter. The p95 spikes are noise on a loaded PC.
- **Index needed: no**, so no backlog row.
- **When to revisit:** a store or supplier with tens of thousands of live listings would aggregate them all before sorting. That is the same DEC-041 volume note Discover already carries.

## Design review (styleseed-design-review)

- **Round 1: 96/100 (A).** Coherence 20, Colour 16, Hierarchy 16, Layout 9, States 12, Copy 11, Motion 12.
  - **Layout −3:** the chip row sat 16 px from the filters and 16 px from the count line, so it didn't read as part of the filter group.
  - **Copy −1:** "#404, not found" is terse inside the Remove label.
- **Fix:** the chips moved into the toolbar's wrap, 8 px under the filters and 16 px above the count.
- **Round 2: 99/100 (A).** The copy nit is left as backlog row 1.
- **Also fixed:** repeated e2e runs found three more problems, each fixed with a test:
  - A chip's dark skeleton was invisible, because `--skeleton` equals `--secondary` in dark. The bar now uses `bg-foreground/10`.
  - A name loading projected a one-frame scaleX, even under reduced motion. Fixed with `layoutDependency`.
  - Focus could drop to the body after the last chip was removed. It now goes to the other chip, else the h1.
- **UI bar:**
  - every state is designed: loading, empty, error, stale, and no source yet (the existing "No products collected yet", shown when there are no filters);
  - keyboard-only use works, with a visible ring;
  - reduced motion is honoured and asserted;
  - tokens only;
  - AA: the chip's muted label and the foreground name use the same tokens as the filter labels;
  - no horizontal scroll at 375 px, asserted.
