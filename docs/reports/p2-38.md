**The task** (DEC-278 a–c):
- **Days.** With no args it computes yesterday's UTC date. `start` and `end` are ISO dates and backfill inclusive: `end` defaults to yesterday and `start` to `end`. So `start` alone runs through yesterday, and `end` alone runs that one day.
- **Per day.** It calls `pulso_ml.features.daily.run(session, day)`, then `session.commit()`, then logs `features_done day=… written=…`. A failure stops the range; the days before it stay committed, and a re-run writes 0 rows for them.
- **Refusals.** A range that reaches today (UTC) or is reversed raises `ValueError` before the database opens. Rows are append-only, so a day computed before its cutoff would keep a partial row for good.
- **Flag off** (the default): it logs `features_disabled` and never opens the database, like `MATCHER_ENABLED` / `EMBEDDINGS_ENABLED`.
- **Beat entry: not here** (DEC-278 d). The collector host has no `-Q ml` consumer yet (DEC-269 g, imp-284), so a scheduled send would sit unconsumed in Redis. The entry for imp-284 to add is `"ml.features": {"task": "ml.features", "schedule": crontab(minute=0, hour=7), "options": {"queue": "ml"}}`. Unlike `ml.embed`, this task needs no `clip` extra or weights. Once it's scheduled, the owner turns `FEATURES_ENABLED` on.

**The end-to-end test** (DEC-278 e):
- **Setup.** It loads the leakage fixture's `build()` from `packages/ml/tests/test_leakage.py` by file path, since test folders aren't packages here. It runs `run()` and a commit for days 8–45, the way the backfill would, then calls `GET /v1/products?sort=momentum`.
- **Order oracle.** The response must equal each live product's latest feature day with a V7 and a G7, taking the best grade on that day (DEC-239 c), sorted by G7 then id descending, with insufficient signal last.
- **Order by hand.** The order is also pinned by hand: **P5, P4, P3, P2, P1, P7**.
  - P5 speeds up: C3 sells 8 a day from day 36 and merges in on day 40. G7 ≈ +0.288 on day 45.
  - P4, P3 and P2 hold steady: G7 = 0 on day 29, with ids breaking the tie.
  - P1's CJ dips on day 45 (G7 ≈ −0.034), which outranks its higher-graded Shopify row from day 29. The latest day comes first.
  - P7 has a V7 since the split (3 on day 45) but no G7 yet.
  - P6 is merged into P5 and doesn't appear.
- **Card fields.** Each card's `value` (rounded V7), `growth`, `family`, `grade`, `gap` and `as_of` (the day's cutoff) equal that row's.
- **Unknown never reads 0.** Cards with no row answer `{"value": null, "reason": NO_SIGNAL}`. P2's newest rows are unknown (its listing oversells from day 36), so its card keeps day 29's V7 with day 29's `as_of`. P7's V7 without a G7 reads as insufficient signal.

## Leftovers and ceilings

- **Stale velocity on Discover:** a product whose newest rows are unknown keeps showing its last known V7 (P2: day 29's), as DEC-239 (c) says. The card's `as_of` names that day, but `stale` is only set when the source's config has `expected_interval`. The migration-seeded sources in the test database have none, so P2 read `stale: false` 24 days after its as_of. Check that the collector host's `shopify_stores` and `cj` rows carry `expected_interval`; if they don't, Discover never marks a velocity stale.
- **Backfill cost:** each day re-reads each family's whole history (p2-35 "AsOf.levels"). 38 fixture days took 0.6 s; measure on real history before a long backfill.
- **Fixture by path:** the API test executes `packages/ml/tests/test_leakage.py` to reach `build()`. If that file is renamed or `build`/`START`/`P` change shape, this test fails loudly. Moving the fixture into a shared importable module is the fix once a third consumer appears.
