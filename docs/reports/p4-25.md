## Behaviour (DEC-337)

- **Request:** `GET /v1/pulse?date=` returns `{day, cutoff, sections}`.
- **The day:** the window is [d 00:00Z, d + 1 00:00Z), and `cutoff` is d + 1 00:00Z. Every number reads only captures before the cutoff.
- **Default day:** the date of the newest `scores` row by id, else yesterday.
- **Section contract:** each section has `status` (ok | empty | no_source), `as_of`, `sources`, `reason` and at most 10 items. A merged product reads as its survivor.

| Section | Rule | Sources | No source when |
|---|---|---|---|
| `emerging` | Trend among Lifecycle emerging/rising on d, highest first, `since_yesterday` | scores trend, lifecycle | no Trend row on d |
| `movers_up` / `movers_down` | Trend d vs d − 1, same `model_version` only; `old`, `new`, signed `change`; up > 0, down < 0 | scores trend | no Trend row on d |
| `new_in_stores` | first seen on d in tracked stores, published within 7 days before the cutoff | shopify_stores | crawler disabled (DEC-261) or no tracked store |
| `alerts` | fired on d, not archived, unread first then newest; `unread` count | alerts | never (empty when quiet) |
| `watchlists` | up to 20 lists, `item_count`, 10 newest items. Each item has a 14-day Trend series, Trend since yesterday, `stage_before` / `stage` and d's alert types on its offers | watchlists, scores | no list |
| `margins` | landed margin re-costed at both cutoffs under today's settings (dated economics), both present and different; `old_bps`, `new_bps`, `change_bps` | `workspace_product_economics` | no settings, or no store or supplier listing before the cutoff |
| `suppliers` | supplier listings with a snapshot on d: price change (same currency) and `in_stock()` flip; flips first | cj | no supplier listing |
| `search` | d's `gt_interest` rows at the current `FEATURE_VERSION` by abs(`gt_slope`); `change_pct` = e^slope − 1 | google_trends | no row on d |

**Dated economics.** `dated_economics()` reads migration 0014's frozen view text and edits it in three places, asserting the count of each edit:

- the snapshot and freight tables become `captured_at < :cutoff` subqueries;
- `delisted_at IS NULL` becomes "live until its delisting time";
- the rows are filtered to the workspace and the candidate ids.

`test_the_dated_view_at_a_late_cutoff_is_the_live_view` holds it to the live view. A later migration that changes the view fails that test until `dated_economics()` reads the new text.

**Finding: margins have no source while Shopify is off.** The view's market price comes only from store listings. With the crawler off (DEC-261) and no CSV store prices, `margins` is always `no_source`, with the reason "No market price yet: a margin needs a store price and a supplier price."

**Finding: CJ stock never reaches `in_stock()`.** CJ writes inventory only to `variant_snapshots` (`inventory_quantity`). The listing-level stock readers miss CJ stock-outs: the Suppliers tab, the R-23 alert rule and this section. This is a backlog row so it is fixed once, rather than adding a second stock rule here.

## Bounded queries and index use

Statements per section are fixed, independent of the number of rows:

| Section | Statements |
|---|---|
| scores (emerging + movers) | 4 |
| alerts | 1 |
| new_in_stores | 3 |
| watchlists | 9 |
| margins | 9 |
| suppliers | 4 |
| search | 3 |
| default day | 1 |

That is 33 per request, plus 1 when `date` is omitted. The day's alerts are read once and shared with the watchlists.

**Fixture.** EXPLAIN (ANALYZE, BUFFERS) ran on a year-long fixture in a throwaway schema:

- 3,000 products and 3,500 listings (3,000 CJ, 500 store);
- 1.46 M `scores` rows (2,000 products × 365 nights × Trend and Lifecycle);
- 573.5 k `listing_snapshots` and 73 k `shipping_options`;
- 839.5 k `product_daily_features` rows;
- 6,000 alerts and 165 watchlist items.

The script is not committed.

| Section | Main query plan | Time |
|---|---|---|
| scores | Bitmap Index Scan on `uq_scores_kind_product_id_date_model_version`, skip scan (2,001 index searches) | 22 ms + 34 ms |
| alerts | Bitmap Index Scan on `ix_alerts_workspace_id_fired_at_id` | 0.06 ms |
| new_in_stores | Index Scan on `ix_listings_store_id` per tracked store | 0.14 ms |
| watchlists | Index Scan on `uq_scores_kind_product_id_date_model_version` for the series; `watchlist_items` seq-scanned (165 rows) | 0.7 ms |
| margins: candidates | Bitmap Index Scan on `ix_listings_store_id`, then `ix_listings_product_id`, then one `LIMIT 1` probe per listing on `ix_listing_snapshots_listing_id_captured_at` / `ix_shipping_options_listing_id_captured_at` | 3.4 ms |
| margins: dated view ×2 | every snapshot and freight read is an index scan (often backward) on the `(listing_id, captured_at)` indexes, 167 candidates | 65 ms + 55 ms |
| suppliers | `ix_listings_supplier_id`, a `LIMIT 1` probe per listing (3,000), then 4 backward laterals on `ix_listing_snapshots_listing_id_captured_at` for the 1,334 that changed | 140 ms |
| search | Index Scan on `pk_product_daily_features`, skip scan (2,001 searches) | 14 ms |
| default day | Index Scan Backward on `pk_scores`, 1 row | 0.05 ms |

That is about 335 ms of database time for the whole payload against the note's 600 ms p95 guess.

**Before the perf commit, on the same fixture:**

- `max(scores.date)` was a seq scan (269 ms).
- The suppliers candidate `EXISTS` was a Hash Right Semi Join over a Parallel Seq Scan of `listing_snapshots` (136 ms).
- The margin candidates seq-scanned both capture tables (52 ms) and re-costed 500 arbitrary products, none with a store price (2 × 210 ms, all `supplier_cost_missing`).

**Ceiling.** The two stock laterals in `suppliers` walk an offer's snapshots backward until one carries stock. CJ offers never carry listing-level stock (see the finding), so each walk reads the offer's whole history. That is about 0.05 ms per offer at a year of history. A partial index on stock-bearing snapshots (a migration) is the upgrade if it grows.
