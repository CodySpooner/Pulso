## What changed

| File | Change |
|---|---|
| `apps/api/src/pulso_api/auth.py:47-48` | The `auth_unavailable` 503 branch also catches `json.JSONDecodeError` and `UnicodeDecodeError`. These come only from the JWKS fetch: PyJWT 2.15.1's `fetch_data` wraps `URLError`, `TimeoutError` and `HTTPException`, but its `json.load(response)` errors escape unwrapped. Token parsing can't raise them: PyJWT turns its own header/payload `ValueError`s into `DecodeError`, a `PyJWTError`. |
| `apps/api/tests/test_api.py` `test_invalid_jwt_rejected` | Two new cases: a validly signed token with no `exp` and one with no `iat` → 401 `bad_token`, with `provision_principal` not called. |
| `test_unknown_kid_rejected` (new) | An RS256 token signed by a throwaway RSA key generated in the test, with `kid` `other-key` → 401 `bad_token`, no provisioning. |
| `test_unconfigured_auth_is_503` (new, ×2) | `clerk_issuer` unset, or `clerk_jwks_url` unset → 503 `auth_unconfigured`. |
| `test_jwks_fetch_failures` (new, ×4) | The real `PyJWKClient.fetch_data` runs; only `urllib.request.OpenerDirector.open` is replaced. `URLError` → 503 `auth_unavailable`. An HTML body → 503 `auth_unavailable` (was 500). A Latin-1 body (`<html>\xe9</html>`, not valid UTF-8) → 503 `auth_unavailable` (was 500). `{"keys": []}` → 401 `bad_token`. No provisioning in any case. The `jwks_client` cache is cleared before and after. |

**One step past the brief:** the brief names only the JSON decode error. A non-UTF-8 body fails earlier, inside `json.loads`, with `UnicodeDecodeError`, and the red run showed it as a separate 500. A proxy error page in Latin-1 is a plausible "not JSON" body, so the same branch catches it. I named both exceptions instead of catching `ValueError`. A bare `ValueError` would also cover any future stray `ValueError` from `jwt.decode` and report it as an outage.

No accepted token changes: every changed path ends in an error response, only the status code (500 → 503) differs.

## Known ceilings (not changed)

- **JSON that isn't a key set** (`{}`, `[]`, `{"keys": []}`) stays 401 `bad_token`, because PyJWT raises `PyJWKClientError`/`PyJWKSetError`, which are `PyJWTError`s. aud-013 and the brief both keep it that way. A misconfigured `CLERK_JWKS_URL` that serves valid non-JWKS JSON therefore looks like a bad token, not an outage. If that matters, map `PyJWKSetError` from the fetch to 503 as well. That is a status-code decision for the owner or a later row.
- **A bad body is not cached.** `fetch_data` raises before its cache write, so each request re-fetches until the endpoint recovers, bounded by the 3-second timeout. This is unchanged and is the same as a network outage.
