### p2-20 money math · clear, XR-38 low

- **New lines:** `net = fit(margin − ad_cost)` and `net_bps = fit(round(Fraction(net × 10,000, price)))`, half-even like `margin_bps`. Both are withheld whenever anything is missing (R-16).

- **Pick:** `best()` still ranks on `margin_minor`, before ads, and every row gets the same ad cost, so at sane values an ad cost can't change the pick. At extreme values it can (XR-38).
- **Loader:** `Calc.inputs` is the exact `Inputs` priced. `days` comes from the chosen quote's row. `quoted` never reuses the request's `method` for the next listing (p2-20's mutation 11/11).
- **Router:** `duty_bps` is null under DDP. `payment_fee_*`, `shopify_fee_bps` and `returns_bps` are the inputs' own. Source names come from `sources.name` and owner labels. `stale` follows DEC-238 and is never set for owner input.

### p2-25 undo, unlink and the CTE · XR-36 medium, XR-40 and XR-41 low

- **Superseded check:** the group is every row with the decision's actor and `decided_at`. It may be undone only while each listing's latest row (by id) is the group's own. Undoing twice, undoing an undo and undoing the matcher's rows all refuse. The API commits once per call, so one transaction is one decision.
- **Reactivation guard:** a `from` product that has been merged since reactivates only for a `merge` row whose product still points at its `to`. Anything else is a 409 ("undo that merge first").
- **Candidates:** only rows the decision's transaction stamped. Apart → `pending` with `decided_at` null; together → `accepted`, which is DEC-260's own rule for same-product pairs.
- **Concurrency:** each call takes the lock before any entity load. The router loads no listing or product before the call, so no stale identity-map row is read. Ids follow lock order (DEC-266 b).
- **What the matcher sees after an undo:** a reject's undo is a `reject`, which `manual()` skips. The undo of a split, a merge or an unlink leaves the listings on a product, which the matcher never moves anyway. The undo of an accept leaves them product-less with an owner `unlink` row, so `manual()` freezes them (XR-36).
- **CTE:** `UNION` (not `UNION ALL`) ends a cycle. Every read and the PUT delete filter on the caller's `workspace_id` (p2-25's test: B sees 0 of A's).
- **Failure mapping:** a merge or split `into` a missing product hits an FK, and the global handler answers 409 `conflict`. That fails closed (observation).

## Findings

### XR-36 · medium · p2-25 · an undone accept leaves owner `unlink` rows, so the matcher never links those listings again

- **Where:** `packages/ml/src/pulso_ml/matching/decisions.py:148-154` (`accept → unlink`) and `:209` (the compensating row carries the undoer as actor); `matcher.py:474-486` (`manual()`: an owner's latest non-reject move freezes the listing); `link()` at `matcher.py:404` refuses a manual mover.
- **Failure scenario** (the committed strict-xfail test, from the probe):
  1. A supplier listing (cost $10) and a store listing (0.83, queued) form a pending pair.
  2. The owner presses A, then U: two `accept` rows, then two `unlink` rows (`undo #…`). Both listings are product-less again.
  3. A new store listing matches the supplier listing at 1.0 with a sane markup.
  4. The run leaves all three product-less, and the new pair stays `pending`. **Without the accept and undo, the same run links them** (control probe).
- **Impact:** DEC-263 (b) says the undo restores what the matcher saw. Instead, a misclick-and-undo silently removes both listings from auto-linking for good. Their pairs fill the queue at 1.0. A supplier listing is usually the hub every store listing of that product links through.
- **Fix:** `manual()` skips an undo row and the row it reverses. Undo needs the undone row to be the listing's latest, so it is the listing's previous non-reject row. Read the listing's non-reject rows newest first: skip a row whose reason starts with `undo #` together with the row before it, and decide on the next. About ten lines. The probe patch made the test XPASS, and the other 37 tests passed. Refine DEC-263 (b), or record it in the fix task's DEC. If the owner prefers the freeze, amend DEC-263 (b) and delete the test instead. imp-273 (awaiting merge) also changes `decisions.py`, so rebase carefully.
- **Test:** `test_xr36_an_undone_accept_leaves_the_listings_free_for_the_matcher` (`packages/ml/tests/test_matcher.py`, `xfail(strict=True, raises=AssertionError)`).

### XR-37 · low · p2-29 · `popular_products` has no TRUNCATE guard

- **Where:** `0009_popular_products.py:98-101`: a row-level `BEFORE UPDATE OR DELETE` trigger only. 0005 (`match_decisions_no_truncate`) and 0002 (`source_events_no_truncate`) add a statement-level `BEFORE TRUNCATE` trigger with the same function.
- **Failure scenario** (probe): `TRUNCATE popular_products` succeeds in a transaction (rolled back in the probe).
- **Fix:** a new migration adding `CREATE TRIGGER popular_products_no_truncate BEFORE TRUNCATE ON popular_products FOR EACH STATEMENT EXECUTE FUNCTION reject_append_only_mutation()`. 0009 can't be edited once the host runs it. It can ride with the next migration task.

### XR-38 · low · p2-20 · an ad cost the request accepts can withhold the margin and change the pick

- **Where:** `landed_cost.py:149-152`: `fit()` on `net` and on `net_bps` appends `amount_out_of_range`, which then withholds the margin too (`if missing`). `routers/profit.py:69`: `ad_cost_minor` accepts 0..2^63−1.
- **Failure scenario** (probe): two complete rows with margins −600 and −1,100 rank row 1 at ad cost 0 or $15. At `ad_cost_minor = 2^63−1`, both read `amount_out_of_range`, `complete = false`, and `best()` returns None. A positive-margin row at that ad cost loses its margin too (`net_bps` overflows).
- **Impact:** only at absurd inputs (beyond ~$10^16), and it fails closed. But DEC-256 (a) says an ad cost never changes the pick.
- **Fix:** keep net out of R-16. A net or `net_bps` past BIGINT leaves `net_minor`/`net_bps` null without adding to `missing`. Or bound `ad_cost_minor` in the request and in Settings to a sane maximum. Add one core test.

### XR-39 · low · p2-29 · DEC-267 (f) holds by convention only: a global table holds one retailer's licensed data

- **Where:** `models/collection.py:54-77`: no `workspace_id` ("global market data"). The rows are Google's Popular products for one Merchant Center account, which Google licenses for that retailer's internal use only ("can't be … aggregated across businesses"). `availability` is that retailer's own inventory status.
- **Today:** clear. No route reads the table, and the only router without sign-in is `/health`. The raw bucket has no public ACL. v1 has one workspace.
- **Failure path:** once a second workspace exists (SaaS), or once p2-29b's endpoint is built on the global-table assumption, any workspace reads the owner's licensed rows.
- **Fix:** decide it in p2-29b's DEC, before the surface ships. Either scope the rows to the importing workspace (a `workspace_id` through a migration), or have the endpoint serve only the workspace that imported the capture. Add a test that a second workspace reads none. Note it in DATA_SOURCES.

### XR-40 · low · p2-25 · a tag PUT on a merged group moves the merged product's tags, and undoing the merge doesn't move them back

- **Where:** `routers/products.py:720-740`: the PUT deletes this workspace's tags across `with_merged(T)` and inserts them all on T. `undo()` restores listings and `merged_into_id` only.
- **Failure scenario** (probe): S has tag `Gift`. Merge S into T; T reads `[Gift]`. PUT T `[Gift, Q4]`. Undo the merge: S reads `[]`, and T reads `[Gift, Q4]`.
- **Fix:** document it in DEC-263 (d), since the PUT already says it replaces across the group. Or have the PUT keep a tag on the product that already holds it, inserting only new tags on the survivor. Fold it into imp-274 (the tag-cap row).

### XR-41 · low · p2-25 · a user `reason` starting with `undo #` makes a decision un-undoable

- **Where:** `routers/matching.py:180, 188, 198`: `reason` is free text up to 500 characters. `decisions.py:171`: undo refuses any decision whose reason starts with `undo #`.
- **Failure scenario** (probe): POST `reject` with `reason: "undo #1: x"` → 201. Undo it → 409 "decision 3 is the matcher's or an undo; neither is undone". XR-36's fix would read that prefix too.
- **Fix:** have the API refuse (422) or prefix a user reason that starts with `undo #`. Better, have the service mark undo rows by something a caller can't type: the undo's own fixed reason prefix, applied only inside `undo()`, plus a check in `record()`.

## Observations (no fix requested)

- **p2-26, Profit's default pick vs Best margin:** without `?supplier=`, the Profit tab and every margin that uses the default pick can cost a known out-of-stock listing that Suppliers never picks. It is p2-26 backlog row 2, and it is a money-path change that needs its own DEC-072 review. This review endorses doing it.
- **p2-25, a split's cannot-link outlives its undo:** the `split` row stays, so `apart()` still holds the listing apart from its old product's group. That is moot while the listing sits on that product, because neighbours exclude its own product. It would matter only if the listing later left the product without a split. Note it in DEC-263 (b).
- **p2-25, a merge that moves no listing writes no decision:** for example, merging a product an undo emptied (imp-273). The API answers `id: null` ("moved nothing"), so it can't be undone and leaves no history row. Harmless, since nothing moved.
- **p2-25, any signed-in user can undo another user's decision:** consistent with `/v1/admin` being global admin in v1. Revisit with roles.
- **p2-25, an FK miss answers 409 `conflict`, not 404:** merge or split `into` a product id that doesn't exist. It fails closed.
- **p2-29, re-downloads:** a second download of the same week and category with different bytes is a new capture with a full set of ranks (DEC-028). p2-29b should read the newest capture per (country, category, `observed_for`), and DEC-267 (d)'s weekly change should compare newest captures.
- **p2-29, the Filters values:** `Country = US` and `Category = A > B` are modelled from the owner's line, not confirmed against its values. The owner's first import confirms them, together with thousands separators in rank or price (already Owner To-Do 1).
