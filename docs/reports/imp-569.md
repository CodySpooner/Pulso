# imp-569 — the watchlist sparkline test is deterministic

Claude worker, Orca task `task_fc1c494c39df`, dispatch `ctx_528cab97657c`. Branch `CodySpooner/imp-569-flaky-watchlist-test`, rebased on `origin/main` `ab5a9131` (p4-35 and imp-565 merged after the first checks on `80a4db67`). Not pushed or merged. Tests only: no production code, migration or API shape change. DEC-358 is unused, because the fix records no rule.

## Cause

`apps/api/tests/test_watchlists.py::test_items_spark_velocity_reads_the_page_in_one_batch` (imp-419) checked the 7-day line on `items[0]` of a `limit=1` page. The page is ordered `added_at desc, product_id desc`. p1, p2 and p3 are added in one POST, so they share one `added_at`, and their random UUIDs decide which row comes first. p3 has only gap rows, so its spark is the `NoSource` object (`{value: null, reason}`) with no `points`. When p3 had the largest UUID of the three, `week["spark"]["points"]` raised `KeyError: 'points'`. That happens to about 1 run in 3. It is the same failure that the p4-35 report (row 6) and the 03:00Z lead run saw.

Reproduced before the fix: **5 of 15** runs failed, each with `KeyError: 'points'` at `test_watchlists.py:455`.

The ordering itself is right. `(added_at, product_id)` is a total order that matches the cursor (`tuple_(added_at, product_id) < after`), so pages are stable. A tie on `added_at` inside one add request is by design, and `test_items_page_newest_first_and_stable` already covers it.

## Fix

The 7-day check now reads the whole page (`days=7, limit=100`), keyed by product:

- the rows with points number exactly 99 (every row but p3), and each carries exactly 7 points;
- p1, picked by `product_id`, carries the last 7 days of the 30-day `days` list, oldest first.

So it still proves that a `days=7` page carries 7 points per row that has points, and now on every such row, not just the first.

**The rest of the file, checked for the same reliance:**

- every other order assert reads a single-row list (`items(...) == [p0]`, `[p1]`, `[p2]`);
- or reads by product (`added()`, `rows[...]`, `feed[...]`);
- or compares against the order sorted on `(added_at, product_id)` (`test_items_page_newest_first_and_stable`);
- or compares two reads of the same page (`plain == page`).

The statement-count asserts (`limit=1` vs 50/100) don't depend on which row is first: `resolve()` runs one query per merge level, and no product on those pages is merged. In `test_items_read_the_product_now…` the `limit=1` row is always a filler, because the fillers are added last.

**Not changed:** the test takes `end` (yesterday UTC) at its start, and the router takes it per request. A run that straddles 00:00Z would fail, but that needs a test of about 2 s to cross midnight, so it is about 0.002% of runs. It is out of this task's scope; add a frozen clock if it ever shows up.
