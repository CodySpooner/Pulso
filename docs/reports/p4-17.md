# p4-17 — SC-6 append-only scores and the nightly scoring job

Task `task_73ba793a41ba` / `ctx_b5c0c6c51d58`, branch `CodySpooner/p4-17-sc6-scores-job`, Claude. DEC-326 (proposed). Folds in imp-382, imp-397, imp-413, imp-426, imp-427 and p4-14's demand `as_of` row.

One job scores UTC day d from its stored `product_daily_features` rows. It computes Saturation, Trend (with the Saturation penalty) and the Lifecycle stage, then appends rows through `pulso_core.scores.write`. It never updates or deletes, and never scores a day that has no feature rows. There's no migration, no Beat entry, no new flag, and no change to the alerts code or any UI.

## Behaviour (DEC-326)

- **What's scored.**
  - Saturation: every product with a `shp_sellers` row on d.
  - Trend and Lifecycle: every product with a demand-family row (`cj_stock`, `shp_inv`) on d.
  - Only the current `FEATURE_VERSION` is read, and only rows dated d and d−7 (plus first-row dates up to d, and the d−1 lifecycle rows).
- **Primary family (rules 1–3).** Of a product's demand families with a row on d, the one with the earliest first row wins; a tie goes by name. Trend and Lifecycle share it. A family change restarts hysteresis, and `days_observed` counts the new family's own days. With Shopify off, `cj_stock` is the only live family.
- **Insufficient signal (imp-426).**
  - A product in the set with no value gets a NULL row. The explanation is `{model_version, config_digest, components: [], missing: [], coverage: 0, reason}`, so `latest()` returns tonight's NULL with its reason instead of last night's value.
  - A product outside the set (no demand family, no seller row) gets no row, which means "no source".
- **Lifecycle row.**
  - `stage` is the shown stage. `reason` is tonight's rule, and `pending` is tonight's stage while it's held.
  - Inputs: six unweighted components (`<fam>_v7`, `<fam>_v7_prev`, `<fam>_g7`, `<fam>_acc` from `family_velocity`, `days_observed`, `age_days`). `coverage` is the share present.
  - Age: the earliest `source_created_at` (else `source_published_at`) among the product's listings at the cutoff. A launch date at or after the cutoff is ignored, because a re-crawl rewrites today's value.
  - Delisted: the product has listings and every one was delisted before the cutoff.
- **Hysteresis (imp-382).** The night before's row must be the same version and the same family. A different stage tonight keeps the stored stage, with tonight's as `pending`. The stage switches when the night before's `pending` matches tonight's. A no-stage night stores no stage (a gap is never bridged), and the night after it holds nothing.
- **`days_observed` (imp-397):** (d − first row date) + 1, passed to both `family_velocity` and `lifecycle_stage`.
- **`as_of` (imp-427).** A present component whose row has no capture time gets the cutoff d+1 00:00Z. `gt_slope` keeps `gt_as_of`. A missing component keeps None.
- **Running it.**
  - `ml.scores` scores yesterday by default, or `day="YYYY-MM-DD"`. It refuses a day still being collected.
  - `ml.features` scores each day it writes, in order, so a features backfill scores those nights too (DEC-326 a: missed nights only once their feature rows exist).
  - CLI: `uv run python -m pulso_ml.scores.nightly 2026-10-24`.
  - Both run behind `FEATURES_ENABLED`.

## Ceilings (ponytail notes in the code)

- **Category mapping:** normalisation reads today's `products.category_id`, which has no history.
- **`as_of` precision:** the cutoff is within a day of a demand input's newest capture (a present G7 means d was covered). An exact time needs FS-1 to store it (backlog).
- **Read cost:** each night scans every first-row date up to d and replays membership once. Bound both if a night measures slow.
