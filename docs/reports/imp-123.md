## What changed

All changes are in `apps/web/src/components/data-health/sources-table.tsx`, plus one extraction in `atoms.tsx`, which it already imports.

- **There is one failure path per action** (ready for imp-134). Both `setEnabled`'s and `runNow`'s `onError` call `setNotice(actionFailure(source, action, error))`, which records the source key and the error. Where the failure shows depends only on state, never on how it failed:
  - **While its confirm dialog is open:** inside `ReasonDialog`, between the reason and the buttons. The dialog stays open and Submit keeps focus (it was already `aria-disabled` and never `disabled`). Submit retries with the same reason. Cancel, Esc and the overlay close the dialog and clear the failure, so neither the next dialog nor the status line shows it stale. The status line stays empty for it, and the panel behind the modal is `aria-hidden`, so the failure has no second copy.
  - **Otherwise, below md:** in the source's phone card, directly under the switch / Run now row (16 px under the button). The status line hides error notices below md (`max-md:hidden`), so it can't also show at y = −87.
  - **From md up:** the Sources status line, exactly as before (the text plus "(error ID …)"). The new card copy exists in the DOM but sits inside the `md:hidden` list, so it is neither shown nor announced.
- **`ActionError`** shows the failure beside its control. It has three parts:
  - a `role="alert"` paragraph with what failed, why and the next step. This is the only live region carrying the failure, and the error ID and Copy are left out of the announcement;
  - the error ID in a `SelectableId`, `inline-block`, so on a phone it moves to its own line whole;
  - `CopyButton` "Copy error ID". It reuses PanelError's parts, and both come from the shared `copy-button`.

  The ID is `text-muted-foreground`: `subtle-foreground` measured below 4.5:1 on the dialog's error tint in dark (see Design review). On mount the box runs `scrollIntoView({ block: "nearest" })`, with a scroll margin that clears the phone's bottom bar, so a failure from a card near the fold is still seen without scrolling. The scroll is instant, so there is no motion, and rows never animate.
- **Copy.** "Couldn't enable / disable / start {source}: {problem.detail}". When the API never answered, it reads "the API didn't answer. When it runs on your PC, check that the PC is on.", which is imp-078's PC/API next step. The old "Couldn't change …" now names the action.
- **Clearing.** A new attempt (switch, Submit, Run now) drops the last *failure*, so a repeated failure is a fresh alert and is announced again. A success notice stays until it is replaced, so the 1440 status line doesn't flicker when the next action starts.
- **Focus.** The switch was `disabled` while saving, so a keyboard user's focus dropped to `<body>` whenever a dialog-less enable took time. The new e2e measured this with a 300 ms reply. The switch is now `aria-disabled` while saving and ignores changes, the same pattern `RunButton` uses. Its dimmed look comes from the existing `aria-disabled:opacity-50`. Focus is never lost, so `useTakeLostFocus` isn't needed.
- **imp-126.** imp-073's tap-toggle moved out of `StatePill` into `TapTooltip` in `atoms.tsx`, which takes the hint plus the trigger's props; `StatePill` behaves exactly as before. An unavailable `RunButton` now renders `<TapTooltip hint={blocker} asChild>`:
  - a tap toggles the reason ("Live collectors run only on the collector host." or "Enable the source before running it.") right above the button, inside the card;
  - nothing is sent;
  - hover and keyboard focus are unchanged;
  - the hint is click-through, like imp-073's.

## Tests

New file `apps/web/e2e/data-health/action-failures.spec.ts` (10 tests). It adds a route that answers PATCH `/v1/admin/sources/*` and POST `…/run` with a 503 problem body (or aborts the request). All 10 failed on `main` for the reported reasons (no error in the dialog, nothing in the card, the old copy, no tap hint), and all pass now.

- **Failed disable** (1440 and 375). Each run checks:
  - the cause, the error ID and Copy error ID are in the viewport inside the dialog;
  - the dialog's `alert` holds the failure text, and exactly one visible live region carries it;
  - Submit keeps focus, and a retry sends the same body. The second failure is a new alert node (re-announced) and still the only one;
  - Cancel closes the dialog, returns focus to the switch and leaves no stale text. Esc closes a failed dialog too, and once the API answers, Disable closes the dialog with "Google Trends disabled.";
  - there is no horizontal scroll.
- **Failed Run now** (1440 and 375):
  - cause and ID in view, one live region, focus kept;
  - 1440: the status line text is byte-for-byte the old format;
  - 375: the alert sits in the card that holds the button, 0–32 px below it, with Copy error ID in view;
  - a later successful run replaces the failure.
- **Failed dialog-less enable (D1)** (1440 and 375): pressed by keyboard, with a 300 ms reply. Cause and ID are in view, one live region, focus stays on the switch, and at 375 the failure is in the FX card.
- **Transport error at 375:** the PC next step, with no Error ID and no Copy.
- **Touch at 375 (imp-126), two cases:** CJ off the host and FX disabled with the host allowed. One tap shows the reason with the bubble within 16 px of the button, a second tap hides it, and 0 non-GET calls are made.
- **Desktop:** hover and keyboard focus still show the reason, and a click sends nothing.

## Design review (styleseed)

- **Round 1, 93/100.** Color discipline was 10/16: the error ID in `subtle-foreground` on `negative-muted` over the dialog's `popover` measured below 4.5:1 in dark, using the repo's own `contrast.test.ts` math with the pair added temporarily (the edit was reverted, since that file belongs to another owner).
- **Fix.** The ID changed to `muted-foreground`, which passes over `card` and `popover` in both themes. The same temporary run also covered `foreground` and `negative` on that tint.
- **Round 2, 99/100 (A).** The one point left is optional: the "Couldn't …" lead isn't weighted apart from the cause.

The UI checklist holds:
- tokens only;
- keyboard reachable with visible focus (Disable after a failed submit, the switch after a failed enable);
- reduced motion honoured: nothing new animates, the scroll is instant and no list row animates;
- AA in both themes;
- no horizontal scroll at 375 (asserted).

The new surfaces are error states of existing views; their loading states are the existing "Saving…" and "Queuing…".
