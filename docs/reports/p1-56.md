## Per area

### JWKS / auth · clear

- **Stampede:**
  - The cooldown check runs in `JWKSClient.fetch_data` (`auth.py:40-47`), and PyJWT calls that only inside `get_signing_key`'s `_client_lock` (an `RLock`). The thread that fetches during an outage is the only one that waits out the timeout.
  - Every thread queued behind it then reads `retry_at` under the same lock and fails at once.
  - The test `test_jwks_outage_answers_queued_requests_from_one_fetch` and the probe both show 1 fetch.
- **No lockout after recovery:**
  - `retry_at` is set only when the real fetch raises an `OUTAGE` error (`:45-46`). The cooldown's own `PyJWKClientConnectionError` is raised before the `try`, so it never extends the window.
  - The first request after 5 s fetches for real. Valid tokens see at most 5 s of 503 after the endpoint recovers (probe).
  - A cached key set is served without calling `fetch_data`, so the cooldown never touches it. A failed fetch never clears the cache: PyJWT writes the cache only after a successful fetch.
- **Clock:** `time.monotonic()`, so a wall-clock step can't stretch or skip the window.
- **Threads and processes:**
  - Reads and writes of `retry_at` happen under the client lock.
  - `jwks_client` is an `lru_cache` per process, so each uvicorn worker has its own window. That means N workers make at most N fetches per 5 s during an outage, which is acceptable.
- **503 vs 401:**
  - `OSError` joins `OUTAGE` (`:31`). Inside `verify_token`'s `try` (`:59-68`), only the JWKS fetch does I/O, so no token defect can surface as `OSError`.
  - Malformed tokens still answer 401 before any fetch (probe).
  - `{"keys": []}` stays 401 without a cooldown, as DEC-226 (a) says.
- **No unverified token gets through:** every cooldown path raises, and no path returns a key without `jwt.decode` checking the signature, `iss`, `exp`, `nbf`, `iat`, `sub` and `azp`.

  - Features follow DEC-031 either way.
  - It weakens the first-run diagnosis DEC-230 relies on.

## Observations (no fix requested)

- **JWKS bodies that aren't key sets:** JSON `null`, `[]` or `{"keys": []}` answers 401 `bad_token` with no cooldown, so each request makes one quick fetch. DEC-226 (a) chose this for `{"keys": []}`, and `null` and `[]` take PyJWT's same `PyJWKClientError` path. This is outside imp-151's diff.
- **The first fetch still holds the lock:**
  - The fetch that starts an outage still holds PyJWT's lock for its whole timeout.
  - urllib's `timeout=3` applies to each socket operation, so an endpoint that trickles bytes can hold it longer.
  - The cooldown only helps once that fetch ends. This predates imp-151, and Clerk is the only endpoint involved.
- **The DEC-230 ceiling also covers catch-ups:**
  - A catch-up just after 00:00Z stores same-day rows that are early blends.
  - First-rate-wins keeps them, as it keeps 17:00Z same-day blends.
  - data-06 didn't change this, and its proposed backlog row (FX same-day early blends) covers it.
