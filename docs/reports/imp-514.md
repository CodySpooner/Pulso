## Why the default breaks readers

Today a CJ listing gets `listing_snapshots` rows from three capture kinds: catalog (`/product/listV2`), detail (`/product/query`) and CSV. All three carry the same fields: price range, `listed_count` and currency. So the latest row is always a complete one, and most readers take one latest row per listing.

The stock capture (`/product/stock/getInventoryByPid`) carries no price. Under the default, its listing row would have `price_min_minor` null and would become the latest row whenever stock changes. A later price change would then write a row with `stock` null.

## Rejected fixes (DEC-343)

- **Stock-only listing row** (the default): breaks the readers above.
- **Complete rows** (the stock row copies the latest price; catalog, detail and CSV rows copy the latest stock): every reader would work unchanged and no migration is needed. But DEC-112 says "do not copy price into stock captures or claim inventory from detail pricing", and DEC-120 rules out carry-forward. A copied price would cite the stock capture's `raw_payload_id` and `captured_at`, so its as-of and source-on-hover would be false. If a run's detail request failed, a days-old price would read as fresh.
- **`in_stock()` reading variants:** the 0014 pick mirrors `calculate()` (DEC-291), so this needs the same view migration. It would also need variant reads in the Suppliers, Discover, Pulse and R-23 readers. It is not smaller.

## Related bug (on main today)

`unit_cost(listing, variant)` returns `None` for every CJ variant once a tracked run has written its stock row. The newest variant row is the stock writer's, whose price is null. DEC-120 fixed change-only per writer and added `current_fields()`, but this P2 reader still takes the single latest row. A Profit calc with a chosen CJ variant therefore has no unit cost. The fix is `current_fields(..., writers=VARIANT_WRITERS)` or a price-writer filter in `unit_cost()`. It belongs with the follow-up, since that task changes `unit_cost()` anyway.

## Follow-up for the lead (one task, view migration on 0023)

1. **Writer** (`pulso_sources/cj/tracked.py`): the stock capture also appends a stock-only `ListingSnapshot`. `stock` is the sum of the payload's variant totals when every variant is known, and null when any variant is unknown or none are listed. Its evidence (`captured_at`, `observed_for`, `raw_payload_id`, parser version) is the stock capture's. It is change-only under a listing stock `Writer` (stock endpoint, owns `stock`).
2. **Price rows:** `CJAdapter.upsert` (catalog, detail, CSV) takes a listing price `Writer` (any capture not from the stock endpoint), so alternating captures stay change-only (DEC-120). This also settles DEC-156's open "listing writer split" follow-up.
3. **Readers** (each above that breaks):
   - Price reads skip stock-writer captures. `unit_cost()` and the view's unit lateral already join `raw_payloads`.
   - Stock reads take the newest row that has stock fields or comes from a stock-writer capture. An unknown total supersedes an older level (DEC-120), unlike `alerts.latest()`'s non-null filter today; decide that once for all readers.
   - `unit_cost(variant)` reads the detail writer's price.
4. **View:** one migration on 0023 edits the unit-cost lateral and the 0014 stock lateral. Pulse `dated_economics()` must then read that revision's text; its `count == 3` assert on `listing_snapshots snap` changes with it. `test_the_dated_view_at_a_late_cutoff_is_the_live_view` guards that.
5. **Acceptance:** keep this brief's (1)–(5), plus: a CJ listing with a stock row latest keeps its unit cost in `unit_cost()`, the Suppliers tab and the economics view.
