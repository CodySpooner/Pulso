### XR-23 · medium · p2-14 · an origin whose newest answer lists no method, or a quote with no origin, keeps its old price and can win "cheapest"

- **Where:**
  - `packages/core/src/pulso_core/landed_cost_loader.py:138-143`: `rank()` over `(coalesce(variant), origin_country)`, ordered by `captured_at DESC, raw_payload_id DESC`, only over `shipping_options` rows.
  - `landed_cost_loader.py:154`: rank 1 per partition.
  - `packages/sources/src/pulso_sources/cj/tracked.py:96-109`: one CJ freight request per (variant, origin), CN and US.
  - `cj/tracked.py:117-121`: a `data: []` answer parses to no records, so the writer adds no row (`:196-211`).
  - `cj/csv.py:169`: a CSV quote's origin is the row's `warehouse_country`, which may be blank. A blank origin is its own partition.
  - `apps/api/tests/test_profit.py:438, 458`: p2-14's own test asserts that a 29-day-old US capture still prices `USW` while CN has a newer capture.
- **Defect:** "the newest capture" is the newest one that wrote rows. An answer that lists no method is a capture, but it leaves no row, so the partition's newest visible capture is the older one. Its methods stay priced as current. DEC-250 (a) says a method the newest capture no longer lists is never priced; that fails when the newest capture lists nothing. This is the limit case of XR-16's own scenario: a carrier drops the route, and it was the only method for that origin.
- **Failure scenario** (probe, `POST /v1/profit/calc`, price 2999, unit cost 620, duty 0, the p2-10 fee settings):
  1. Day 1: CJ answers (V, CN) `CJPacket` $5.00 and (V, US) `USPS` $3.00.
  2. Day 30: (V, CN) answers `CJPacket` $5.00. (V, US) answers `{"code": 200, "result": true, "data": []}`: the raw payload is stored, and no row is written.
  3. The response says `method: "USPS"`, `freight_minor: 300`, `complete: true`, `margin_minor: 1812`, and `sources.freight.as_of` is day 1.
  4. Against the only freight on offer, the margin is $16.12. It is $2.00 too high, and it is presented as complete.
  5. `method: "USPS"` answers 300 and complete, where XR-16's rule says `freight_missing`.
- **Second path** (probe): a CSV `manual` quote of $2.00 with no warehouse stated, 29 days old, next to CJ's day-30 CN capture (`CJPacket` $5.00, `ePacket` $4.50). The call answers `manual` 200, complete.
- **Impact:** no UI reads the endpoint yet. UX-8 part b, UX-6 and Discover's best margin will. US-warehouse quotes come and go with CJ's US stock, which makes the CN/US pair the common case.
- **Fix:** pick one; either way, the fix task records it as a refinement of DEC-250 (a).
  1. **Loader only:** first take the newest capture day per variant across origins (`observed_for`; CJ captures CN and US in the same run), then the newest capture per origin within that day. An origin with nothing on that day isn't priced. A failed or empty US request then reads as "no US quote", which fails closed (R-16).
  2. **Or record empty answers:** keep the newest freight capture per (variant, origin) from `raw_payloads`, so a capture with no rows prices nothing for that origin. Or have the CJ writer persist an explicit no-quote marker.
  3. **CSV with no origin:** under rule 1 it ages out with its day. Under rule 2 it needs its own rule, for example merging it into the variant's partition.
- **Test:** `test_xr23_an_origin_whose_newest_answer_is_empty_is_not_priced` in `apps/api/tests/test_profit.py`, marked `xfail(strict=True)`. It expects `CJPacket` 500 and margin 1612, and `method: "USPS"` → `freight_missing`. The fix task removes the mark.
  - Its payload names the variant (`products[0].vid`), so the test holds under either fix.
  - The fix should also add tests for the two mutations that survive today (see Mutations): a newest capture with two methods where the requested one is not first, and a re-parse.

### XR-24 · low · p2-13 · the top 20 neighbours counts image rows, so one listing with many embedded images crowds out the others

- **Where:** `matcher.py:72-78`: `ORDER BY distance LIMIT k` over `images` rows. `matcher.py:136-139`: the rows are folded by listing after the limit. DEC-249 (e) says "its top 20 listings".
- **Failure scenario** (probe): source S (store A, 0°) and target T (store B, 4°). Both are $10 retail, and cos 0.9976 makes them a sane auto-link.
  - N1 (store B, 0.5°, $1,000) and N2 (store A, 5°, $1,000) each have 21 embedded images.
  - S's 20 rows are all N1's, and T's are all N2's. Each listing excludes its own store's crowd.

- **When it matters:** a listing gains image rows whenever its store changes an image URL. The Shopify writer adds a row per new URL and never removes the old one (`shopify_stores/records.py:253-256`). Today nothing is embedded (M-2 part b), so it is latent.
- **Fix:** take k distinct listings (`DISTINCT ON (listing_id)` over an over-fetched inner limit, or de-duplicate while fetching), or embed one image per listing. **Test:** the probe.

### XR-25 · low · p2-13 · pending rows stay in the queue after they stop being queue-worthy

- **Where:**
  - `matcher.py:190-198`: an existing `pending` row is re-scored in place. A `discard` verdict only counts it.
  - `matcher.py:155-157`: a pair already on one product is skipped before its row is looked at.
  - `matcher.py:82-85`: same-product listings are never neighbours.

### XR-26 · low · p2-13 · one bad row stops the whole matcher run, and every later run stops at the same listing

- **Where:** `matcher.py:118`: `to_usd` raises `ValueError` past BIGINT (p2-14's report noted this as an observation). `score.py:71`: `max()` on a NaN `Decimal` raises `InvalidOperation`. `matcher.py:121-199`: no per-listing isolation.
- **Failure scenarios** (probes):
  - A GBP listing at `price_min_minor` 2^63−1 with a 0.79 rate → `ValueError`.
  - A zero-norm `title_embedding` on a neighbour → pgvector's cosine is NaN → `InvalidOperation`.
  - In both cases, a later supplier/retail pair that would link stays product-less. Listings run in id order, so every run stops at the same row.
- **Impact:** it fails closed (no wrong write, a loud error). Neither input occurs today: no FX-converted price is near 2^63, and OpenCLIP vectors are unit-norm. But one corrupt row stops all matching after it.
- **Fix:** no USD price on `ValueError`, and a non-finite cosine counts as missing. Optionally, roll back and log per listing. **Test:** the two probes, with the later pair linked.

### XR-27 · low · p2-13 · the matcher's FX lookup ignores CSV rates and carries a rate forward with no age limit

### XR-28 · low · p2-13 · four matcher rules have no test that fails without them

- **Fix:** the four matcher-level tests in the table above.
- **Expected survivors (no fix):** removing `SET LOCAL hnsw.iterative_scan` and removing the pair's `FOR UPDATE`. Starving the top 20 needs more rows than a unit test holds, and the lock only matters with two concurrent runs, which `worker_concurrency` 1 rules out.

## Per area

### p2-13 append-only history (R-15) · clear

- **Only one writer:** only `link()` changes `listings.product_id` (`matcher.py:274-287`). The collectors never set it: `shopify_stores/records.py:160-183` and `cj/__init__.py:193-205` write identity and text fields only, and no production module assigns `product_id` (grep).
- **One decision per moved pointer:** each mover gets exactly one `MatchDecision` (`actor="algo"`, `action="link"`, `from_product_id` NULL, `to_product_id` the canonical target, `candidate_id`, confidence = score, a reason naming `scorer_version`). It is in the same transaction as the pointer change, and a rollback takes both.
- **Movers are re-read under lock:** `FOR UPDATE` with `populate_existing` (`:252-259`), so `from_product_id` NULL is true at write time.
- **Never touched:** `accepted`, `rejected`, `merged` and `split` rows (`:165-166`). The 0005 trigger rejects UPDATE, DELETE and TRUNCATE on `match_decisions` (`0005:120-136`). The matcher only inserts there.
- **Manual and transitive constraints:**
  - A listing whose latest decision isn't `algo` never moves (`:309-317`).
  - The veto checks the mover's rejected and split partners against the whole merged group (`:292-306`). It holds whichever side moves, because a pair is stored once and matched on either listing (read, and the veto mutation fails p2-13's bridging test).
- **Products are never emptied or split:** only product-less listings move.
- **Tests:** p2-13's R-15 universe test, plus the mutations below.

### p2-13 USD markup gate · exponents right; XR-26, XR-27 low

### p2-13 threshold edges · clear
