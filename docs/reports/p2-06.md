## Choices (DEC-242)

- **(a) Only robots.txt keeps the count.** Every other live answer still resets it, as DEC-069 says. One Shopify gap remains: a store whose `/meta.json` answers 200 and whose `/products.json` answers 429 on every run still resets at `/meta.json`. That answer is the store's own JSON. The run still stops at the 429 and honours `Retry-After`, 403 marks the store blocked, and 430 disables at once. If the lead wants that case counted too, it needs its own decision (left out of scope).
- **(b) `NoListedHost` also fires in a steady state.** It isn't only a typo: once every listed host's images are stored, a day with only off-list images due also reads `partial`. That is deliberate. Those images have no pHash, and the fix is to list and check their host. Nothing pending still reads `success`. A `partial` run queues no catch-up (`apps/workers/src/pulso_workers/ops.py:127-132` only retries `failed`, `skipped` or missing slots).
- **(c) Strict validation, not silent normalising.** One consequence: `Settings` is shared, so a malformed `IMAGE_HOSTS` stops every process that loads settings (API and all workers), not just `listing_images`. That matches the other collector limits, which fail the same way.
- **(d) The skip keeps per-host spacing and limits.** It only stops one host's delay from ending the run for the others. The fetch-time deadline check stays as the backstop.
- **(e) The largest Crawl-delay anywhere in the file**, not only in PulsoBot's group, so another bot's stricter delay also slows us.

## How XR-12 changes imp-198 (not amended here)

imp-198 plans a framework-level "nothing to do = success" and wants `listing_images` to drop its plan capture. After DEC-242 (b), its acceptance should say that a day whose due images are all on unlisted hosts still reads `partial` with a named `NoListedHost`, and that only a day with nothing due, or only images in backoff, reads healthy. So whatever replaces the plan capture must still be able to end the run `partial` with that code.
