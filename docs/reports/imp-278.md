## Root cause

The Trends tab composed each click's new URL from the last render's `range` and `on`. The URL can be ahead of that render.

1. `set()` writes the URL at once with `window.history.replaceState`.
2. Next 16.4.2 patches `replaceState` and syncs `useSearchParams` through `restore()`. That function dispatches `ACTION_RESTORE` inside `startTransition` (`next/dist/client/components/sequential-router-queue.js`). In dev it is wrapped once more in the dev rendering indicator's transition (`use-action-queue.js`). So the tab re-renders a little later, at transition priority.
3. A second click before that re-render runs the old closure. `toggle()` used the stale `range` (7d) and the stale `on` ([demand, price]), so it wrote back `range=7d` and undid the All click. That is exactly the URL CI received.

**The trace.** I ran the test with an init script that logged every `history` write and click (it was never committed):

| CPU | All click → Next commit | All click → next click | Result |
|---|---|---|---|
| 1× | ~70 ms | ~145 ms | passes, about 75 ms of margin |
| 3× | commits only after the second click | ~280 ms | fails 3/3; the 7D click is lost before the reload too (`?tab=trends&overlay=demand%2Cprice`) |

**Not a click before hydration.** The toolbar only renders after the series fetch on the client. The trace also shows the All click's own `replaceState` firing.

## Fix

`apps/web/src/app/(app)/products/[id]/trends.tsx`: the range buttons and pane toggles now read the current state from `window.location.search` at click time (`current()`, through the existing `readState`). The render still comes from `useSearchParams`. Discover's `set` already works this way, and so does the Sellers `f` key ("the URL, ahead of a re-render").

This fixes the cause rather than masking it. The URL is the state, and it changes synchronously. Building each click on the URL makes the result independent of when React re-renders: every click is applied once, on top of the one before. Nothing waits and no timeout was added. The original test is unchanged: one click each, the URL holds the state, and the series is fetched once per page load.

**Regression test** (`trends.spec.ts`, "a second click before the tab re-renders still builds on the first"). It clicks 7D and then "Stores selling it" in one browser task, which always beats the transition. It expects `range=7d&overlay=demand%2Cprice`, then both `aria-pressed` values.
- Before the fix it failed 3/3 with the CI symptom (`?tab=trends&overlay=demand%2Cprice`).
- After the fix it passes.
- The throttled trace now passes 3/3 at both 3× and 6× CPU; before the fix it failed every run.
