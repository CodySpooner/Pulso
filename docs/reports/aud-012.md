## Inferences (not verified)

- **I1. The Excel round-trip is modelled, not run in Excel.**
  - The model applies four transforms: ISO date to `M/D/YYYY`, `true` to `TRUE`, `5.00` to `5`, and 12+ digit numbers to scientific notation. It follows W2–W4 and Excel's en-US defaults; Excel was not run.
  - The owner's Excel version and locale are unknown. A non-US locale would write `D/M/YYYY` instead, which is why E-20 keeps dates ISO-only and asks for a named error rather than a second accepted format.
- **I2. Real IDs are long enough to be mangled.**
  - Live Shopify product and variant IDs and CJ product IDs commonly have 12 or more digits, which would put them in Excel's exponential display.
  - This was **not checked against live data**: no source requests in this task, and the repo fixtures use placeholder IDs.
  - E-21 holds for any 12+ digit numeric ID however long the real ones are, because the parser accepts the mangled text either way.
- **I3. Leaving the example row in is a plausible slip.** An owner who fills the template below its example row and forgets to delete it is exactly the case Shopify warns about (W1). Pulso can't repair it in place: history is append-only (AGENTS.md §3), and the FX first rate stands (F3).
- **I4. The preview might not catch it.** imp-080 (unmerged) will show the example row in the "Valid rows" sample, which may help the owner spot it. The FX example looks plausible (`2026-01-01, USD, JPY, 150`) and has no "Example only" marker.

### E-19 · P1 · Template example rows never import as observations

- **Evidence:**
  - URL 1 (accessed 2026-10-23): Shopify's sample "contains two example products", and the user must "remove all the example products". The platform relies on the user. Shopify can overwrite or delete a product afterwards; Pulso's history cannot be fixed in place (AGENTS.md §3) and must hold no fake data (§2).
  - Repo: F1–F4.
- **Metric:** template example rows that a commit accepts.
  - Baseline: **4/4 parse valid**. **2/4 commit on `main`** (FX and Trends), pinned by `test_service.py:33–38` and `test_fx.py:58–62`.
  - That becomes 4/4 once P1-51 and P1-52 merge.
  - Target: **0/4**.
- **Acceptance:**
  - A data row equal to its template's example values is a row error: "This is the template's example row. Delete it before importing." The comparison runs after the parser's normal trimming.
    - Alternative: make the example row unparseable by design. The implementer picks one and records it under its own DEC.
  - Preview counts that row as invalid. A file that holds only the example row finishes `no_valid_rows` and keeps its raw evidence, as today.
  - Tests that used `template_csv(...)` as a valid fixture switch to explicit fixture bodies: `test_service.py` parametrized over all 4 templates, `test_fx.py`, and `test_csv.py:17, 261, 330`.
  - New tests cover each of the 4 templates: the unchanged template yields 0 valid rows, and the template plus one real row yields exactly 1.
  - The panel's template link (or the template itself) says that the example row is rejected.
  - **Out of scope:** existing stored rows. If an example row has already been imported on the collector database, removing it is a destructive data operation and goes to the owner. This audit did not query that database.
- **Target:** Phase 1, now; FX and Trends imports are live. Fold the Shopify and CJ halves into P1-51 and P1-52 if they haven't merged, otherwise the fix covers them through the shared parser.
- **Agent:** Codex or Claude. Shared parser plus tests, about 40 changed lines.
- **Gates:** none. It only makes validation stricter.

### E-20 · P2 · Row errors show the accepted form, and Excel re-saves of Pulso's own templates import or name the Excel fix

- **Evidence (all accessed 2026-10-23):**
  - URL 2: Excel converts dates and long numbers on opening a CSV.
  - URL 4: date conversion "can't be turned off"; preformat the cells as Text.
  - URL 1: Shopify recommends Google Sheets for viewing CSVs.
  - Precedent: imp-049 (merged `a97d3de`) fixed the same problem for `rate` only.
  - Repo: F5, F6, probe output.
- **Metrics:**
  - **A.** Failing cell kinds whose row error states the accepted form: **1/8 → 8/8**.
  - **B.** Templates whose modelled en-US Excel re-save either imports or fails with a message naming Excel and the fix: **0/4 → 4/4**.
- **Acceptance:**
  - `parse_csv` keeps `_cell`'s own message for every kind; `rate` keeps imp-049's text. A message may show the received value, at most 40 characters and control characters stripped (the cell is untrusted). Error samples stay capped at 100.
  - Booleans accept `TRUE`/`FALSE` in any case. This is unambiguous, so no data is guessed.
  - Dates stay ISO-only (ambiguous `M/D` versus `D/M`; I1). A cell like `1/1/2026` gets: "Use YYYY-MM-DD. Excel may have changed this date; format the column as Text before saving."
  - The template link, or the panel's empty state, adds one line: "Editing in Excel? Format the date and ID columns as Text first."
  - **Tests:**
    - one per kind for the message;
    - a re-saved fixture per template: the bool cell passes, the date cell gives the Excel message;
    - `interest` `<1` keeps a clear integer message (see "Considered").
- **Target:** Phase 1; the import panel is the §4.2 fallback in use today.
- **Agent:** Codex (parser), with Claude for the one line of panel copy.
- **Gates:** none. The implementer records the boolean tolerance under its own DEC.

### E-21 · P2 · Identifier cells in scientific notation are rejected, never imported

- **Evidence (all accessed 2026-10-23):**
  - URL 2: Excel truncates to 15 digits and shows scientific notation on opening a CSV.
  - URL 3: exponential display applies to numbers with 12 or more digits, and precision stops at 15 digits.
  - URL 5: Matrixify tells users to prefix numbers with ‘ "so that Excel does not convert it to scientific number".
  - Repo: F7, F8. The digits are lost by the time Pulso sees the file, so the only safe outcome is rejection.
- **Metric:** identifier columns that accept a scientific-notation value.
  - Baseline: **3 on `main`** (CJ `cj_product_id` and `sku`, Shopify `sku`). **5 with P1-51** (adds `product_id` and `variant_id`).
  - Target: **0**.
- **Acceptance:**
  - Identifier columns are flagged in the template. Their cells reject `^[+-]?\d+(\.\d+)?[eE][+-]?\d+$` with the message: "Excel turned this ID into scientific notation and its digits are lost. Export the ID column as Text and import again."
  - The P1-51 "Duplicate entity" error names the identity column actually used (`variant_id` when present), not `sku`.
  - **Tests:** one per identifier column; plus two variants mangled to the same value, which must give the scientific-notation error, not a duplicate.
  - Leading zeros that Excel drops (URL 2) can't be detected. The E-20 template line ("format ID columns as Text") is the only guard, and the row says so rather than claiming to catch it.
- **Target:** Phase 1. **Time-sensitive:** fold into P1-51 (which adds the 14-digit-scale columns) and P1-52 before they merge, or make it an immediate follow-up on the shared parser.
- **Agent:** Codex (the P1-51/P1-52 lanes).
- **Gates:** none (stricter validation).
