## Behaviour

**Tables (DEC-314 a):**
- `watchlists`:
  - columns `id` uuid, `workspace_id`, `name` varchar(80), `position` int, `created_at` timestamptz;
  - UNIQUE `(workspace_id, name)`, exact case once trimmed;
  - UNIQUE `(workspace_id, id)`, which the items' foreign key needs.
- `watchlist_items`:
  - columns `workspace_id`, `watchlist_id`, `product_id`, `added_at` timestamptz, `position` int (stored, default 0, not read yet);
  - primary key `(watchlist_id, product_id)`;
  - foreign key `(workspace_id, watchlist_id)` → `watchlists (workspace_id, id)` ON DELETE CASCADE.
- Both tables have `workspace_id` NOT NULL and indexed.

**Endpoints.** The operation id is the function name:

| Endpoint | Operation id | Behaviour |
|---|---|---|
| `GET /v1/watchlists` | `list_watchlists` | Every list with `item_count`, sorted by `position`, then `created_at`, then `id`. Not paged |
| `POST /v1/watchlists {name}` | `create_watchlist` | 201. The new list goes last. A duplicate name is a 409 `conflict`; a blank, too-long or extra field is a 422 |
| `PATCH /v1/watchlists/{id} {name?, position?}` | `update_watchlist` | Renames the list, and/or moves it to a 0-based `position` (past the end means last). Lists are then renumbered 0…n−1. A duplicate name is a 409 |
| `DELETE /v1/watchlists/{id}` | `delete_watchlist` | Returns the list as it was. Its items go with it (the cascade) |
| `GET /v1/watchlists/{id}/items?cursor=&limit=` | `list_watchlist_items` | `product_id`, `name`, `image_url`, `added_at`. Newest first, with `product_id` breaking ties. The cursor is `[added_at, product_id]`; `limit` is 1–100, default 50. A bad cursor is a 422 `invalid_cursor` |
| `POST /v1/watchlists/{id}/items {product_ids[]}` | `add_watchlist_items` | 1–100 ids. A merged product adds its survivor (through any chain of merges), deduplicated. A re-add keeps the first `added_at`. An unknown product is a 404, and nothing is added |
| `DELETE /v1/watchlists/{id}/items/{product_id}` | `remove_watchlist_item` | Idempotent. Returns the list |
| `POST /v1/watchlists/{id}/items/move {product_ids[], to}` | `move_watchlist_items` | Each item keeps its `added_at`; if `to` already holds the product, the earlier one wins. Products not on the source list are skipped. Returns `to` |
| `PUT /v1/products/{id}/watch` | `watch_product` | Creates "Main" (placed last) and the item in one request. A second PUT changes nothing. Returns `{watchlist_id, product_id (the survivor), added_at}` |
| `DELETE /v1/products/{id}/watch` | `unwatch_product` | Removes the product, and any product merged into it, from Main. Returns the removed item, or null |

**Isolation:**
- Another workspace's list answers 404 `not_found` on every `/v1/watchlists/{id}…` route, as source or as move target.
- The database refuses an item whose workspace differs from its list's.

- **First star creates Main and the item in one request; a second PUT is a no-op that keeps `added_at`.** `test_first_star_creates_main_and_a_second_is_a_noop`:

  - the second PUT's body equals the first, `added_at` included;
  - the items page shows name, image and `added_at`.

  The same test also covers:
  - a merge chain (merged → middle → p0) stars p0, and an unknown product is a 404;
  - unstar returns the item, and a second unstar returns null;
  - a product merged *after* its star is removed by unstarring the survivor;
  - a deleted Main comes back with the next star, placed last.
- **Add, move, remove and delete-list behave as specified.**
  - `test_items_add_move_and_remove`:
    - 4 ids add 3 items (the merged id is p0);
    - a re-add keeps every `added_at`;
    - an unknown id is a 404 and adds nothing, and an empty list is a 422;
    - a move into a list that already holds p1 keeps A's earlier `added_at`, skips p5 (not on A), and returns the target's count;
    - moving to the same list is a no-op, and remove is idempotent.
  - `test_lists_are_created_renamed_reordered_and_deleted` covers create, rename, reorder and delete, with the 409s, the 422s and the cascade.
- **404 for another workspace's list; the two-workspace isolation test covers both tables.** `test_workspace_b_never_sees_or_edits_a`:

  - A's lists and items are unchanged;
