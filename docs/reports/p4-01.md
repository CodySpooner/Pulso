## What was built

| Piece | Where | What |
|---|---|---|
| Table | `migrations/versions/0016_scores.py`, `models/catalog.py::Score` | Global `scores` table. Columns: `product_id`, `date` (UTC day), `kind` (`trend`, `saturation`, `lifecycle`, `risk`, `refund_risk`), `model_version`, `value numeric(5,1)` (0–100, NULL when every input is missing), `stage` (lifecycle only, with NULL `value`), `explanation jsonb`, `computed_at`, bigint `id`. UNIQUE `(kind, product_id, date, model_version)` |
| Append-only | same migration | The 0005 `reject_append_only_mutation()` trigger function rejects UPDATE and DELETE (row) and TRUNCATE (statement). The downgrade refuses while any row exists |
| Explanation contract | `pulso_core.scores.Component`, `Explanation` | Pydantic v2, frozen, extra keys refused. `Explanation` holds `model_version`, `config_digest`, `components`, `missing` (validated against the components) and `coverage`. `Component` holds `name`, `family`, `source`, `weight`, `weight_eff`, `raw`, `z`, `contribution`, `as_of`, `missing`, `gap`, `ai_derived` and `prompt_version`, which is required when `ai_derived` (DEC-047) |
| Version | `pulso_core.scores.version(config)` | `{revision:03d}-{sha256[:12]}` plus the full digest of a frozen config dataclass: the `FEATURE_VERSION` rule. The helper was **not** moved, so `pulso_ml` is unchanged |
| Renormalisation | `pulso_core.scores.explain(config, components)` | A missing input gets `weight_eff` 0 and no contribution; the present inputs get `w / Σ present w`. Returns `Σ weight_eff × z` (None when nothing is present) and the explanation. A present input without a z raises |
| Writer | `pulso_core.scores.write(session, rows)` | `INSERT … ON CONFLICT DO NOTHING RETURNING id`; returns the new-row count. The row's `model_version` comes from its explanation |
| Reader | `pulso_core.scores.latest(kind)` | A `Select` of each product's newest row of that kind (latest date, then newest `computed_at`, then `model_version`). It's served by a backward scan of the unique key, and callers add filters and joins |

## Open points for the lead and owner

- **SPEC §5's `scores` line lists wide columns** (`trend_score`, `saturation_score`, …, `lifecycle_stage`). DEC-306 (a) maps them to one row per `kind` and keeps SPEC unedited (no amendment-log edit in this task). If the owner keeps this, SPEC §5's wording could follow in an owner-approved amendment.
- **Contribution units.** `contribution` is `weight_eff × z`, in z units; Trend and Saturation points are 50/3 × it. If SC-2 prefers to store points, that's a contract change it records under its own DEC.
- **p4-02 versions lifecycle differently.** p4-02 (SC-4, DEC-307, dispatched in parallel, not merged) has its own `version()` giving `lifecycle_v0-<hash8>`, following the vault's old §2 wording. DEC-306 (d) sets `{revision:03d}-{hash12}` through `pulso_core.scores.version`.
  - Nothing breaks: `model_version` is a free `String(80)`, and `latest()` breaks ties on `computed_at`, not on the version text.
  - Recommendation: when SC-6 starts storing stages, Lifecycle uses `pulso_core.scores.version(CONFIG)` (giving `000-<hash12>` for p4-02's `revision = 0`), so every kind shares one format. Otherwise DEC-306 (d) should be changed to the vault format. The lead decides at merge.
  - **Lifecycle explanations.** Lifecycle doesn't combine weighted z-scores, so it builds an `Explanation` directly rather than through `explain()`: its inputs (V7, G7, Acc, age) as components with weight 0, and `coverage` set to the share of inputs present.
