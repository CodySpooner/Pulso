## Cause

- **XR-63:**
  - **The window was too wide.** `step()` started the gap window at `state["at"]`, the previous *snapshot row*. CJ's listing snapshots are change-only, so that row is the last value change, not the last capture. Any gap since the last change held the crossing.
  - **A hold never confirmed.** A held crossing waited for a new row, and an unchanged price never writes one.
- **XR-64:** `step()` rebuilt `status` and `skipped` on every evaluation, and kept nothing per offer. So an offer with no new observation reported `ok` while its crossing was still held.
- **The `as_of` bound:** reads used `captured_at <= as_of` and `detected_at <= as_of`. p4-23 passes the day's cutoff, d+1 00:00Z, so a capture made exactly at the cutoff (it belongs to day d+1) was read into day d (DEC-031).

## The default I took (coordinator question unanswered)

The brief says to stop and ask if `collector_runs` can't express "a complete run that re-observed the offer" without a schema change. They can't, exactly:
- A run records that it completed, not which listings it held. CJ's catalog panels are ranking-bounded.
- An unchanged offer writes no row.
- `collector_run_targets` is one target per category plan, not one per listing.
- `Listing.last_seen_at` is current-only, not point in time.

**What happened:** I asked through `orca orchestration ask` (message `msg_f1a1de349d9b`). There was no reply in 2 × 10 minutes, so I built on the default I offered there.

**The default:** a successful, complete run of the offer's source counts as re-observing every live offer of that source, which matches how `offers()` already treats a CJ listing as live until it's delisted. This applies to price and stock rules only. It is recorded as DEC-335 (e), with a `ponytail:` comment in `seen()`.

**If the lead wants per-offer evidence:** that's a migration (backlog row 1 below).
