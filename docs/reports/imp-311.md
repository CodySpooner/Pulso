# imp-311: a NUL character in any free-text API input answers 422, not 500 (DEC-287)

Follow-up to XR-32 (imp-267, `docs/reports/imp-267.md` imp-267-b1). Postgres text can't hold NUL. psycopg refuses one on the client with `DataError: PostgreSQL text fields cannot contain NUL (0x00) bytes`, and until this task that error surfaced as a 500.
- **Run:** Claude worker on branch `CodySpooner/imp-311-nul-inputs`, Orca task `task_4bec014a3456`, dispatch `ctx_bc5b99109afa`. Nothing was pushed or merged.
- **Base:** rebased on `origin/main` `60ba49d` (p3-03, p2-39). Nothing on main touched `apps/api/src`, `openapi.json` or `pulso_sources/imports` after `e92e2de`, where this work started.
- **Decision:** DEC-287, `proposed (imp-311)`.
- **Not changed:** no migration, flag or dependency, and no behaviour change for valid input. A tab or newline still gets each endpoint's earlier status (one assertion per case).
- **API shape:** `openapi.json` gains 9 `pattern: ^[^\x00]*$` lines and nothing else. Search's `q` schema is byte-identical, because it moved from its own pattern onto the shared type. `schema.d.ts` regenerated unchanged, since openapi-typescript doesn't emit patterns. The new 422 `invalid_text` code reuses the existing `Problem` body.

## The mechanism

1. **`NoNulStr`** (`apps/api/src/pulso_api/schemas/text.py:6`): `str` with the pattern `^[^\x00]*$`. Every free-text request-body field uses it. FastAPI refuses a NUL before the endpoint runs, with the usual `validation_error` 422 naming the field (`string_pattern_mismatch`).
2. **NUL-only handler** (`apps/api/src/pulso_api/main.py:96`): text that isn't a model field (path, query and JSON cursors) reaches SQL as a parameter. The handler maps a SQLAlchemy `DataError` whose cause says "cannot contain NUL" to a 422 `invalid_text` problem ("Text cannot contain a NUL character."). It re-raises every other `DataError`, so those stay logged 500s (tested). psycopg refuses the NUL before sending the statement, and the request's session rolls back as it does for any error.
3. **CSV:** unchanged. `_cell` (`packages/sources/src/pulso_sources/imports/csv.py:77`) has refused NUL since `41fde51b`. A NUL cell is that row's `Invalid <kind> value` error naming the row and column, and the other rows import. The new tests pin it.

**Checked and not needing a guard:**
- **Settings** (`PATCH /v1/settings`) has no text field: two `Literal`s and integers.
- **CJ activity** (`PUT /v1/admin/sources/cj/activity`): `currency` already has `^[A-Z]{3}$`, and the rest are dates and integers.

- **Other cursors** (notes, Discover, sellers, suppliers, matching queue, popular products, gaps) decode to numbers, dates and UUIDs only.
- **The `__session` cookie** is a JWT and never reaches SQL.
- **CSV headers:** a NUL header is an unknown column, the whole file's existing 422 (`invalid_file`), and a commit stores only the exception's class name.
- **Product keywords:** p3-02's `POST /v1/products/{id}/keywords` is not on `origin/main` `60ba49d`. It should use `NoNulStr` when it lands (backlog row imp-311-b1 below).

## Not here / follow-ups (backlog rows for the lead)

- **imp-311-b1 (P3):** p3-02's `POST /v1/products/{id}/keywords` isn't on main yet. Its keyword field should use `NoNulStr`, with a case added to `TYPED` in `test_nul_inputs.py`. Without that, the handler still answers 422 when the keyword reaches a text SQL parameter. It does not when the text is written inside JSONB: Postgres itself refuses `\u0000` there (SQLSTATE 22P05), and the handler deliberately leaves that error a 500. No current input writes request text into JSONB.
- **imp-311-b2 (P4):** a `\u0000` inside a Shopify JSON import's strings isn't checked before the adapter writes. That run ends `partial` with error code `DataError`: sanitized and HTTP 200, not a 500, but the owner gets no row-level reason. I probed this once on Postgres with a temporary, uncommitted test. The live Shopify crawler has the same exposure if a store's product text holds NUL. A NUL check in the Shopify records parser would give a per-product reason.
