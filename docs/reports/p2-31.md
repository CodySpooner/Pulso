**Checkpoint (DEC-269 a).** OpenCLIP `ViT-B-32` + `laion2b_s34b_b79k` (DEC-237 a), from Hugging Face `laion/CLIP-ViT-B-32-laion2B-s34B-b79K`:
- commit `1a25a446712ba5ee05982a381eed697ef9b435cf`;
- file `open_clip_model.safetensors`, 605,143,316 bytes;
- sha256 `ac4f8c4b88af6d963118cbf40ad93176d092abbedfcb752601ae1866352656e6`;
- MIT licence.

Both encoders give 512 dimensions, matching the existing `vector(512)` columns. Only repository metadata was read from the Hugging Face API; no weights were downloaded.

**What the job writes.**
- **Images.** Every `images` row with a `storage_key` and a NULL `embedding`. The raw payload is found by the indexed `sha256` (named in the key) and read back by `read_capture`, which checks the hash. Then OpenCLIP's image encoder runs on it.
- **Titles.** Every listing whose `title_embedding` is NULL or whose `title_norm` differs from `title`. The job writes the vector and `title_norm = title` together.
- **Batches.** 32 rows, keyset by id, one commit each.

**Idempotency (DEC-269 c).** The brief asks for a key on content hash + model version. That holds without a key column, so no migration:
- An image row's stored copy never changes once set (DEC-240 h), so a NULL embedding means that content hasn't been embedded.
- `title_norm` keeps the exact text each title vector came from. CJ rewrites titles in place, so a changed title is embedded again.
- The model version is fixed by the schema (DEC-237 a: another checkpoint is a migration that clears both columns).

A second run encodes nothing and updates no row. The test checks `xmin` on every `images` and `listings` row.

**Missing images (DEC-269 d).**
- **No stored image.** The listing gets a title vector only. Its image vector stays NULL, never a zero vector, and it counts in `image_missing`, which is the matcher's `skipped_no_embedding` set (DEC-040).
- **Unreadable image.** A missing object, a hash mismatch or undecodable bytes is logged and counted as `image_unreadable`. It is retried next run, and the rest of its batch still embeds.

## Dependencies: how CI and the Dockerfile handle them

- **CI.** It runs `uv sync --locked --all-packages`, which installs no extra, so no CI job installs torch. Confirmed locally: after that sync, `uv pip show torch` reports "not found". `--locked` still checks the regenerated lock. mypy ignores `torch`, `open_clip` and `huggingface_hub` imports, which are absent in CI.
- **Worktrees.** Same as CI: torch-free.
- **Dockerfile.** Not changed; it is outside this task's ownership. Before `EMBEDDINGS_ENABLED` can be turned on, an `ml` worker image or service needs:
  1. `uv sync --locked --no-dev --no-editable --package pulso-workers --extra ml`;
  2. a build step that runs `hf_hub_download("laion/CLIP-ViT-B-32-laion2B-s34B-b79K", "open_clip_model.safetensors", revision="1a25a446712ba5ee05982a381eed697ef9b435cf")` into the image's HF cache;
  3. `HF_HUB_OFFLINE=1` at run time;
  4. a consumer for `-Q ml` at concurrency 1.

  The `collect,default` image (`infra/docker/worker.Dockerfile`) should stay torch-free. Its comment "Phase 2 adds CPU torch/CLIP weights" predates this split. All of this is infra and collector-host work (backlog row below).
- **Lock contents.** `open-clip-torch 3.3.0`, `torch 2.14.1+cpu` (and `2.14.1` for macOS, same index), `torchvision 0.29.1+cpu`, timm 1.0.30, huggingface-hub 2.3.0, safetensors 0.8.0, and their dependencies (sympy, networkx, jinja2, regex, ftfy, tqdm, …). The index has cp314 CPU wheels for Linux x86_64 and aarch64, Windows and macOS.

## Tests

**`packages/ml/tests/test_embeddings.py`** (new, Postgres). It uses a weight-free fake encoder: an image's red level and a title's length set an angle. Images are generated PNG bytes, held in a dict standing in for the object store. The reader keeps `read_capture`'s hash check.
- `test_stored_images_and_all_titles_are_embedded_then_a_rerun_writes_nothing`. Three listings: one with a stored image, one with an unfetched image row, one with no image. The run gives `Counts(images=1, titles=3, image_missing=2)`. The unfetched image's vector is NULL. Each `title_norm` equals its title. The second run gives `Counts(image_missing=2)`, the encoder sees nothing, and every row's `xmin` is unchanged.
- `test_a_changed_title_alone_is_embedded_again`. The only input the second run encodes is the new title.
- `test_an_unreadable_image_is_counted_and_the_others_still_embed`, parametrised `object_missing` and `undecodable`. The failing image gets the log line, a count and a NULL vector; the other image embeds.
- `test_the_matchers_candidates_come_from_the_new_vectors`. Before the run, `match()` skips all 3 listings. After it, the only candidate is the near pair (10° apart), `pending`, with `image_cos` = `stored(cos 10°)` = 0.9848 and `title_cos` 1. The orthogonal listing doesn't pair. No price is set, so it queues and never auto-links.
