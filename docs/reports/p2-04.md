## What it does

| Step | Behaviour |
|---|---|
| Plan | Main image = lowest `position` of a listing with `delisted_at IS NULL`, newest row on a tie (Shopify positions start at 1). Only images with no `storage_key`, on an `https` host listed in `IMAGE_HOSTS` (default empty), and not in backoff. At most `rate × budget minutes` per host (1,350 by default), hosts round-robin. |
| Robots | One robots.txt target per host per run, before its images. Non-2xx: fail closed, the host's images skip the run with no penalty. `Disallow`: the image fails `RobotsDisallowed`. `Crawl-delay` / `Request-rate` slow the host. |
| Fetch | urllib, honest `PulsoBot/0.1 (+PULSO_BOT_CONTACT)` User-Agent, no proxy, no redirects; per-host spacing `60 / IMAGE_REQUESTS_PER_MINUTE` (≤ 30/min); framework guards (`COLLECTORS_LIVE`, worktree, `sources.enabled`), `Retry-After`, 5xx retries, block rule with one disable event. |
| Validate | Before anything is stored: image/jpeg, png, webp or gif; ≤ 5 MiB (reads one byte past at most); ≤ 40 MP from the header; Pillow limited to those formats; full decode. `ImageContentType` / `ImageTooLarge` / `ImageUndecodable`, plus an `image_rejected` warning with the image id (the job id rides in the JSON log). |
| Store | The framework's raw capture is the one stored copy (`raw/listing_images/<UTC date>/<sha256>.bin.gz`); `images.storage_key` is its key, `images.phash` the signed hash. |
| Re-run | A stored image is never planned again. A failed one waits 20 h × 2^(n−1), capped at 30 days, counted from its own run targets (no new columns). |
| Quiet day | With nothing due, one offline JSON plan capture is the run's only target, so it succeeds instead of being recorded failed (which would trigger a catch-up and an overdue status). |
| Schedule | `listing_images.images` daily 06:00 UTC on `collect` (crontab), after the Shopify, CJ and Trends slots. |
