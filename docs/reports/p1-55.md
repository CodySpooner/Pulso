## Money conversion · clear on arithmetic; XR-7 and XR-8 low

- **No floats on the fraction:**
  - `toMinor` (`model.ts:211-217`, `7d05845`: `203-209`) splits the string with `^(\d+)(?:\.(\d+))?$` and right-pads the fraction to the currency's decimals. It then adds two integers: `Number(whole) * 10**digits + Number(fraction)`.
  - Each part below 2^53 is exact. `Number.isSafeInteger` rejects any result at or past 2^53, and an integer part past 2^53 − 1 always rounds to at least 2^53, so it is rejected too.
  - No rounding happens: more decimals than the currency uses → null.
- **Inputs:**
  - Refused: zero, negative, empty, exponent, comma decimal and whitespace-only input.
  - Accepted: leading zeros (`00019.99` → 1999).
  - JPY (0 decimals) refuses any fraction. KWD (3) parses `1.255` → 1255.
- **The server agrees for every currency the project knows:** for all 8 entries of `pulso_core.money.CURRENCY_EXPONENTS` (`money.py:5-14`), `Intl` in Chromium and Node gives the same decimals. Outside that table, see XR-7.
- **The trust boundary:** `amount_minor` is a `StrictInt` above 0 (`cj/activity.py:33`), so strings, floats and `true` get a 422 (imp-161's tests). The BIGINT ceiling that `to_minor` enforces (imp-108) is missing; see XR-7.

## Findings

### XR-7 · low · API + web · the amount's decimals come from the browser, and the API accepts currencies and sizes that `pulso_core.money` can't read

- **Where:**
  - `packages/sources/src/pulso_sources/cj/activity.py:33-34`: `amount_minor` has `gt=0` and no ceiling; `currency` is any `^[A-Z]{3}$`.
  - `apps/api/src/pulso_api/schemas/admin/__init__.py:81`: the same pattern.
  - `apps/web/src/components/data-health/model.ts:212` (`7d05845`: `204`): the decimals come from `Intl` `maximumFractionDigits`.
- **Defect:**
  - The project's only exponent table is `pulso_core.money.CURRENCY_EXPONENTS`, with 8 currencies. Nothing in the write path checks against it.
  - Outside those 8, the web takes the browser's ICU/CLDR digits, which differ from ISO 4217 for some codes:
    - Chromium 156 and Node 24 give IDR 0, HUF 0, IQD 0 and LBP 0, where ISO 4217 gives 2, 2, 3 and 2.
    - A made-up code like `ZZZ` gets 2.
  - The API also has no upper bound, while `to_minor` (imp-108) caps minor units at BIGINT.
- **Failure scenario:**
  1. The owner saves an order of `150000` with currency `IDR`. Chromium says IDR has 0 decimals, so the PUT stores `amount_minor: 150000`.
  2. By ISO 4217, 150,000 IDR is 15,000,000 minor units, so the stored value reads 1,500.00 IDR (100× low). `from_minor(150000, "IDR")` raises `KeyError`.
  3. `ZZZ` is stored as a currency. A direct API call stores `amount_minor` 2^63 or 10^30, past BIGINT.
  4. The probes confirmed every step.
- **Impact:** nothing reads `amount_minor` beyond `> 0` today. The default currency and CJ's billing currency are USD, and all 8 table currencies agree. So nothing is wrong yet. It becomes a wrong-money bug (medium) once anything displays or sums the stored amount.
- **Fix:**
  - In `Evidence` (only the API imports `cj.activity`, so no collector caller changes), check `currency in CURRENCY_EXPONENTS` and bound `amount_minor` with `lt=2**63`. Stored evidence that fails the new checks then reads `unknown`, which is the existing invalid path.
  - In the web, refuse a currency outside the same 8 before saving: a short list, or the API's 422 surfaced. `Intl` stays correct for those 8.
  - Tests: PUT with `IDR`, `ZZZ` and `2**63` → 422 and nothing stored. A Vitest case that `toMinor` refuses an unlisted currency, if the list moves to the web.

### XR-8 · low · web · the amount field's native `step="0.01"` and `min="0.01"` block valid 3-decimal amounts and suggest rounding them

- **Where:** `apps/web/src/components/data-health/sources-table.tsx:805` (`7d05845`: `804`), and `model.ts:213` (`205`) for `.5`.
- **Defect:**
  - The form has no `noValidate`, so the browser checks the field's native constraints before `onSubmit` runs `toMinor`.
  - `step="0.01"` (based on `min`) and `min="0.01"` assume 2 decimals.
  - `toMinor` and its unit test claim KWD support (`1.250` KWD → 1250). That case passes only because its third decimal is 0.
- **Failure scenario:**
  1. Currency `KWD`, amount `1.255`, Save. Chromium blocks the submit with "Please enter a valid value. The two nearest valid values are 1.25 and 1.26." Following that hint stores 1250 or 1260 fils instead of 1255.
  2. Amount `0.005` KWD is blocked as below the minimum.
  3. The reverse case: `.5` USD passes the native check, but `toMinor` returns null. The dialog then says "Enter an amount above 0 with no more decimals than USD uses", which is the wrong reason for a valid 50-cent amount.
  4. The Chromium probe confirmed all three.
- **Impact:** UX only, and KWD isn't the owner's currency. Nothing wrong is saved unless the owner follows the browser's rounding hint.
- **Fix:**
  - `step="any"`, and drop `min`. `toMinor` already refuses ≤ 0 and excess decimals, and its message stays the single source.
  - Let `toMinor` accept a leading `.` (`.5` → `0.5`).
  - Tests: Vitest `toMinor(".5", "USD") === 50`. An e2e that saves `1.255` KWD and checks the PUT body's `amount_minor: 1255`.

### XR-9 · low · API + web · stored evidence observed after the server's now reads `unknown` but still carries its dates, so the row says "No evidence yet" next to "Last order …"

- **Where:**
  - `apps/api/src/pulso_api/routers/admin/__init__.py:140-146`: `as_of` and `observed_at` are set whatever the state is.
  - `packages/sources/src/pulso_sources/cj/activity.py:56`: `observed_at > now` → `Status("unknown", None)`.
  - The web shows "Last order" and "Update order" whenever `as_of` is set: `sources-table.tsx:720, 733, 736` (`7d05845`: `719, 732, 735`).
- **Defect:**
  - The `CJActivity` docstring (`schemas/admin/__init__.py:58`) promises that `unknown` has every other field null, and DEC-216 (b) says the same for missing or invalid evidence.
  - `countdown` has a third `unknown` path, evidence observed after now, and `cj_activity` passes its dates through.
- **Failure scenario:**
  1. The owner saves an order. `observed_at` is the server's now, for example `06:55:11Z`.
  2. The PC's clock then steps back 30 s, as a Windows time sync can do after drift or resume.
  3. Until the clock catches up, `GET /v1/admin/sources` returns `{state: "unknown", days_remaining: null, as_of: "2026-10-21T…Z", observed_at: "2026-10-24T06:55:11Z"}`. The probe confirmed this shape.
  4. The CJ row shows "No evidence yet" with "Last order Oct 21 · Update order".
- **Impact:** the contradiction lasts only as long as the clock skew. It shows no number and fails closed. UX only.
- **Fix:**
  - In `cj_activity`, return the all-null `CJActivity` when `status.state == "unknown"` (one line).
  - Test: in `test_invalid_stored_cj_activity_reads_unknown`, add a stored entry whose `observed_at` is a minute after now → `UNKNOWN`.
