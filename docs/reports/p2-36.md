## The change

| Where | Before | After |
|---|---|---|
| `packages/ml/src/pulso_ml/matching/matcher.py` `manual()` | The listing's latest non-reject row decides. An undone accept ends in the undoer's `unlink`, so the listing is frozen for good. | It reads the listing's non-reject rows newest first. An `unlink` that names a candidate is skipped together with the row before it (the accept it reverses), and the next row decides. No row left means free. |
| `packages/ml/src/pulso_ml/matching/decisions.py` `unlink()` | — | One comment line: an owner unlink names no candidate, because `manual()` reads one that does as an undone accept. |
| `packages/ml/tests/test_matcher.py` | XR-36 test under `xfail(strict=True)`. The undo test's comment said "both frozen". | The mark is removed and a control test is added. The comments now say "both free" and cite DEC-276. |

**Why the row before is the accept.** `undo()` reverses a decision only while each of its rows is its listing's latest row of any action. It writes the compensating row under the same matching lock. So the undo row directly follows the row it reverses, and `INVERSE` maps only `accept` to `unlink`.

**The XR-41 question: why the marker isn't the `undo #` prefix.** A user `reason` is free text, so it can start with `undo #`. `manual()` therefore never reads the reason. It reads the candidate instead:
- `undo()` copies the undone row's `candidate_id`, and every accept names its candidate.
- `unlink()` names none, and nothing else writes an `unlink`. The API router only reads `match_decisions`, and no seed or worker writes it.
- So an `unlink` with a candidate can only be an undone accept. No migration is needed.
- The control test pins this down with an owner unlink whose reason is `undo #<id>: forged`, and M6 below shows the prefix rule would fail it.
- XR-41's own fix is still open in the cleanup row: `undo()` still refuses a decision whose reason starts with `undo #`.

**Why only accept undos need the skip.** `manual()` is asked only about product-less movers (`link()`):
- A product-less listing's latest non-reject row put it on no product, so that row is an unlink.
- An accept moves only product-less listings, so the row before an accept is an unlink too.
- The scan therefore meets only unlinks and the accepts they undo.
- The undo of a merge, a split or an unlink leaves the listing on a product, which the matcher never moves (DEC-276 d).

**Observation recorded in DEC-276 (e), not changed: a split's cannot-link outlives its undo.** The `split` row stays, so `apart()` still keeps the listing apart from its old product's group. That is moot while the listing sits on that product.
