## Behaviour (DEC-334)

- **When:** inside `score()`, which `ml.features` runs after each day it commits and which `ml.scores` runs for its one day. Alerts are evaluated after that day's scores are committed, so a day with no feature rows is still evaluated (supplier-offer rules read snapshots).
- **`as_of`:** the day's cutoff, `pulso_ml.features.daily.cutoff(d)` = d+1 00:00Z, so `fired_at` is that cutoff.
  - A backfill evaluates each day, in order, as of its own cutoff.
  - `evaluate()` reads strictly before `as_of` (DEC-335 a), so a capture at or after a day's cutoff belongs to the next day (DEC-031) and can't fire that day's alert.
  - A re-run fires nothing new (the state moves only on a newer observation or a confirming run; the dedupe key `rule:supplier_offer:listing:date` backs it). A crossing held by a gap still counts as `skipped` on the re-run (DEC-335 d).
- **Per workspace:** `select(Workspace.id).order_by(Workspace.id)`, then evaluate and commit each one.
  - If a workspace raises, it rolls back alone (its seeded defaults, rule state and alerts). The others go on, and the scores are already committed.
  - The failure is logged at ERROR as `alerts_failed day=<d> workspace_id=<id>`. The JSON formatter adds the job id and the traceback.
- **Log, one JSON line per day:** `alerts_done day=<d> workspaces=<evaluated> fired=<new alert rows> skipped=<rules held by a gap> failed=<workspaces that raised>`. The counts go in the message because the formatter's allowlist drops extras, the same as the other ml lines.
- **Gate:** `FEATURES_ENABLED` only, through the chain. No Beat entry. Collector-host behaviour is unchanged until imp-284's slot runs the chain.
- **Data Health job row:** none. `collector_runs.source_id` is a NOT NULL FK to `sources`, so a row would need a pseudo-source seed that Data Health would list as a source. A backlog row is below. Meanwhile, `alert_rules.last_evaluated_at` (the last evaluated cutoff) and the `alerts_done` line show freshness.
