- **XR-63 (p4-15): an R-23 Testing default holds a real crossing because of any gap since the offer's last value change, and never confirms it while the value stays put.**
  - **Where:** `packages/core/src/pulso_core/alerts.py:184-191`. The gap window starts at `state["at"]`, which is the `captured_at` of the previous *snapshot row*.
    - Listing snapshots are change-only (`packages/sources/src/pulso_sources/framework/observations.py:113-125`; CJ writes them through `cj/__init__.py:209`). So that row is the last value *change*, not the last capture.
    - A held crossing waits for "the next new observation" (`alerts.py:179-180`), but CJ writes no row while the price stays the same.
    - The engine test confirms the hold with a snapshot it inserts directly (`packages/core/tests/test_alerts_engine.py:258`). The change-only writer would never write that row.
  - **Failure (probe, through the real `CJAdapter.upsert`):**
    - **Setup:** an open test on a product with one CJ offer at 1000. The PC is off on day 3: there's no capture, and a `host_offline` gap row is written. The price moves to 1100 on day 10 and stays there to day 30. Captures and evaluations run nightly.
    - **Result:** 0 snapshot rows on days 1–9 and 11–30. "Testing: supplier cost change" is `skipped` on day 10, then `ok` from day 11, with `skipped` cleared. It **never fires**.
    - **Without the gap:** the same series fires on day 10. The owner's own rule on the same offer fires on day 10 either way.
  - **Rule:** DEC-324 (e), "the next new observation over a gap-free window fires it". The vault Firing semantics say the R-23 defaults "are suppressed during gaps", not for weeks afterwards.
  - **How likely:** high once imp-465 runs it.
    - The collector host's off nights are expected (AGENTS.md §4) and each one writes a `host_offline` gap.
    - A supplier price is usually stable for weeks. A held crossing confirms only if another hashed field (`listed_count`) changes on a gap-free night.
    - The stock-out default reads the same change-only snapshots. Freight reads `shipping_options`, which are per capture, so freight confirms on its next capture (freight is unscheduled, DEC-321b).
    - **Not live today:** nothing calls `evaluate()` yet.
  - **Fix:**
    - Start the window at the source's newest successful, complete run before the crossing observation (`collector_runs`, `finished_at ≤ as_of`), so it covers only the slots between the capture that last saw the old value and the one that saw the new value.
    - Confirm a held crossing once a later successful, complete run of that source (finished by `as_of`, no gap detected in between) has re-observed the offer, even when the value is unchanged and no snapshot row was written.
    - Test it with `CJAdapter.upsert` (change-only), not direct snapshot inserts: a gap a week before the change fires on the change; a gap the night before the change holds it, then fires after the next gap-free run with an unchanged price.
    - Note the window in DEC-324 (e).

**Low (append to imp-381 if it is still unclaimed: 8/5 → 10/5. Otherwise open a new rolling cleanup row at 2/5. XR-64 can ride with the XR-63 fix, since it's the same function):**
- **XR-64 (p4-15): a held crossing's `skipped` status is lost at the next evaluation.**
  - **Where:** `alerts.py:164`, `:169` and `:202-203`. `step()` rebuilds `status` and `skipped` on every evaluation, and an offer with no new observation (`:179-180`) sets `ok`. Nothing remembers that the offer is still holding a crossing.
  - **Failure (probe):** in XR-63's series, the default reads `skipped` with the gap span on day 10. On day 11 it reads `ok`, with no `skipped`, though the crossing is still held and no alert has fired.
  - **Rule:** DEC-324 (e) ("the rule shows `skipped` with the gap's span"); the vault's Gap-suppressed state.
  - **Fix:** keep a `held` flag (with its gap span) in the offer's state, and report `skipped` while any offer holds one. Add a test for a re-run with no new data.
- **XR-65 (p4-15): a rule on a product, or an open test of a product, stops watching once that product is merged. The rule then reads `no_source`.**
  - **Where:** `alerts.py:55-61` match `Listing.product_id` to the rule's `target_id`, or to the test's `product_id`, as stored. A merge moves every listing to the survivor (`packages/ml/src/pulso_ml/matching/decisions.py:40-45`) and repoints neither.
  - **Failure:** the owner merges a duplicate product that has an alert rule, or an open test. Its offers now sit on the survivor, so the rule evaluates no offer and shows "nothing it watches has data yet" indefinitely, and no alert ever fires for it.
  - **How likely:** it needs a merge after the rule or the test exists. The API's create refuses an already-merged product (409 `merged`, `routers/products.py:726-727`). Nothing wrong is stored.
  - **Fix:** resolve each product id to its survivor (follow `merged_into_id`, as `routers/watchlists.py:115` `survivors()` does) before matching listings. Add a test that merges the product of a product rule and of an open test, then sees the next crossing fire.
