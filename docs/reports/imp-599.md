## The double-offset guard: none needed

Both configs pass `WEB_PORT: String(PORT)` (the final port) in `webServer.env`. If a test worker inherited it, evaluating the config there would add the offset a second time. **Workers don't inherit it**, so no guard is needed. I checked this in Playwright 1.64.1 (`node_modules/.pnpm/playwright@1.64.1/node_modules/playwright/lib/runner/index.js`):

- The web server is launched with a fresh object, `{ ...DEFAULT_ENVIRONMENT_VARIABLES, ...process.env, ...this._options.env }` (about line 872). The runner's own `process.env` is never changed.
- Test workers are forked with `{ ...process.env, ...this._extraEnv }` (ProcessHost, about line 1922). Here `process.env` is the runner's env. `_extraEnv` holds only the env produced by project dependencies and global setup, plus `FORCE_COLOR` and `DEBUG_COLORS` (WorkerHost, about line 5638).
- The runner writes `process.env` in only two places:
  - Global setup's env changes. The Clerk config's `clerkSetup()` adds Clerk testing variables, never `WEB_PORT`.
  - Named groups in a `webServer.wait` regex (about line 930). Neither config uses `wait`.

So a worker sees the same `WEB_PORT` the runner saw (from the shell, or none) and computes the same port. The unit test pins the part that's ours: `smokePort` leaves `process.env` alone, and calling it twice gives the same port. The e2e run below is the end-to-end proof. Workers re-evaluate the config for `baseURL`, so a double offset would point them at 3589, where nothing listens, and the spec would fail. A future Playwright change that leaked `webServer.env` would also fail loudly this way, not silently.
