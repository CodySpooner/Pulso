## What Orca exposes

- **Run history.** `orca automations runs [--id <automation>] --limit N --json` returns `result.runs[]`, newest first. Each run has `id`, `automationId`, `runNumber`, `status`, `terminalSessionId`, `terminalPaneKey`, `terminalPtyId`, `dispatchedAt`, `precheckResult`, `outputSnapshot` and `usage` (with `providerSessionId`). There is no `completedAt` field; `usage.collectedAt` and `outputSnapshot.capturedAt` are stamped at completion. A call takes about 0.5 s with `--id` and 2.4 s across all automations.
- **Statuses.** Orca's bundled `shared/automations-types.js` defines `isFinalAutomationRunStatus` ("statuses a run can never leave"): `completed`, `dispatch_failed`, `skipped_precheck`, `skipped_missed`, `skipped_unavailable` and `skipped_needs_interactive_auth`. The live statuses are `pending`, `dispatching` and `dispatched`.
- **How a lead finds its own run.** No environment variable carries the automation or run id. Every Orca terminal has `ORCA_PANE_KEY` = `<tabId>:<leafId>` (also `ORCA_AGENT_PANE`; `ORCA_TAB_ID` is the tab part). A dispatched run's `terminalPaneKey` has the same form, and its `terminalSessionId` is the tab id. I checked this on my own terminal against `orca terminal list`, and on the records of runs 69 and 70.
- **When a run becomes `completed`.** Per Orca's host service (`orcad-server.js`), a run is `completed` once the agent reports `done` for its pane (its turn ended) and the terminal screen is idle. It becomes `dispatch_failed` if the agent is blocked, never starts, or gives no signal for 6 hours. After that, Orca closes the run's terminal and clears `terminalSessionId`, `terminalPaneKey` and `terminalPtyId`.
- **What the history shows** (2026-10-23/24, from run records and the lead session transcripts):

| Run | Agent's turn ended | Orca `completed` | What followed |
|---|---|---|---|
| 52 | 19:08:06Z, waiting on a background Playwright run | 19:10:06Z | The agent woke at 19:10:53Z and ran `lead_lock.py beat` + `git push` at 19:11:02Z. Its transcript stops with that command unanswered. |
| 65 | 01:42:05Z, waiting on a Monitor ("the push, vault notes and lock release follow") | 01:44:05Z | The session never wrote again. The lock (last beat 01:41Z) skipped run 66. |
| 69 | 03:09:02Z | 03:09:02Z | Terminal ids cleared by 03:11:20Z (my first poll) |
| 70 | 03:17:26Z | 03:17:25Z | Terminal ids cleared by 03:17:34Z (polled every 20 s) |

What follows from this:
- `completed` alone isn't proof that the lead has stopped: run 52 acted after it. A final status *plus* a closed terminal is.
- A lead that ends its turn to wait for background work counts as finished for Orca, which then closes its terminal and its work is lost. That is how run 65 lost the imp-145 merge.
