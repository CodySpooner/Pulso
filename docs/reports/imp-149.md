## Root cause

`execute_run` sets `expire_on_commit = False` on the run session, so after `before_send` commits the reservation, the in-memory `Source.config` stays as it was before the request. `received` then wrote `{**stale_config, "cj_provider_points": …}` back as the whole JSONB value, overwriting any `config` change committed while the request was in flight, such as a `seeds` apply's `config.seed`.

## Why the lock is taken at the call site, not in `record_points`

- `received` is the only production caller of `record_points`. `record_points` takes no session; taking the lock inside it would add a session parameter and touch 13 test call sites.
- The call-site lock is a 2-line diff and matches the existing pattern: CJ `reserve` and the Trends collector (whose `reserve`/`reserve_hourly` say "caller holds the source row lock") refresh the row `FOR UPDATE` before mutating `config`.
- Nothing in session A changes `source` between `before_send`'s commit and `received`, so the refresh drops no pending write.

## The test

1. Session A (the `collect` session) enables CJ and records fixture points (`remaining 50000`).
2. A one-request live run goes through `collect` with `Auth.token` and `Transport.http` faked and the worktree guard patched off.
3. Inside the fake `http`, so after `before_send` commits and before `received`, session B sets `config.seed = {"version": "withdrawn"}` and commits.
4. The response carries different points (`usedToday 50`, `remaining 49950`).
5. A fresh session asserts that `config.seed` survived, that `cj_provider_points.info` is the response's points, and that `cj_points.reserved == 50`.
