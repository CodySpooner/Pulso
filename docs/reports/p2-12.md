### p2-03 migration safety · clear

- **Statement:** `CREATE INDEX ix_products_first_seen_at_id ON products (first_seen_at, id) WHERE merged_into_id IS NULL` (`0007:17-22`), the same in the model (`models/catalog.py:60-67`). `first_seen_at` is NOT NULL, so the index has no NULL keys.
- **Lock:** a plain `CREATE INDEX` takes SHARE on `products`: reads go on, and writes wait. Alembic runs every pending revision in one transaction (`env.py:16`), so a 0004 → 0007 upgrade holds 0005's ACCESS EXCLUSIVE locks and 0007's SHARE lock until it commits.
- **CONCURRENTLY:** not needed, and not possible inside that transaction. It would only matter on a large table with live writers, and the host stops its consumers first (`collector/__main__.py:337`).
- **Duration:** `products` is empty on the collector (DEC-244 lists the non-zero tables, and it isn't one). 200,000 rows took 0.07 s (probe).
- **Collected FX rows:** 0007 doesn't touch `fx_rates` or any collected table. DEC-244's counts after the upgrade match, except 0006's own `sources` row.
- **Downgrade:** `DROP INDEX` only (`0007:25-26`). No data is lost.

### p2-10 rounding and exponents · clear; XR-20, XR-21 low

### p2-10 FX and freight resolution · FX clear; XR-16 medium

- **FX:**
  - The date is the observation's UTC date (`captured_at.astimezone(UTC).date()`) (`landed_cost_loader.py:60`).
  - The rate is the USD-base rate dated `day − 4 … day`, newest date first, with the blend before a `manual` rate on a tie (`:62-73`). A rate dated after the observation's day is never used.
  - No rate → `usd_rate` None → `fx_missing` with the line and the totals null. It is never a guess (`landed_cost.py:70-71, 85-89`).
  - `fx_rates` keys on `(date, base, quote, source)`, so the `captured_at` tie-break never matters.
- **Freight:**
  - Exact quantity (`:129`), destination US (`:128`). There is never a `q × F(1)` fallback.
  - A null-variant quote is accepted only when the listing has at most one live variant (`:111-112, 138-141`).
  - A multi-variant listing with no variant chosen always reads `freight_variant_mismatch`.
  - Only the latest row per `(origin, method)` is kept (`:136-141`). XR-16 is about that choice.

### p2-10 completeness and best margin · clear

- **`complete`:** it is `not missing`. Every null line (price, goods, freight, duty) adds its code, so `complete` holds only when `landed` and `margin` both have a value (`landed_cost.py:91-131`).
- **Duty:**
  - Not set and no DDP → `duty_not_set`, incomplete.
  - Duty 0 is set.
  - DDP → duty 0 and customs 0.
  - An override up to 100,000 bps passes 100%.
- **`best()`:** it ranks complete rows only (`:137-140`), so an unquoted cheap supplier never wins (p2-10 test, re-checked). When nothing is complete, the fallback returns the row with the fewest missing codes. That row's margin is null, so it can't rank.

## Findings

### XR-16 · medium · p2-10 · a shipping method the newest quote no longer lists keeps its last price and can win "cheapest"

- **Where:**
  - `packages/core/src/pulso_core/landed_cost_loader.py:113-135`: every US quote for the listing and quantity, across all history, newest first.
  - `landed_cost_loader.py:136-141`: the latest row per `(origin_country, method)`, however old.
  - `landed_cost_loader.py:147-150, 216-219`: the cheapest in USD wins when no `method` is given.
  - `packages/sources/src/pulso_sources/cj/tracked.py:196-211`: each CJ freight capture writes one row per method it returns, and there is no row for a method it stops returning.
- **Defect:** nothing checks that a method is still quoted. CJ's newest freight response for that variant may no longer list a method, for example after a carrier drops a route to the US. That method's last row stays "the latest quote for that method", so the loader still prices it.
- **Failure scenario** (probe, `POST /v1/profit/calc`, price 2999, unit cost 620, duty 0, the p2-10 fee settings):
  1. Day 1: CJ quotes `Cheap` $3.00 and `Std` $5.00.
  2. Day 30: CJ quotes only `Std` $5.00.
  3. The response says `method: "Cheap"`, `freight_minor: 300`, `complete: true`, `margin_minor: 1812`. `sources.freight.as_of` is day 1, 30 days old.
  4. Against the only freight on offer, the margin is $16.12 instead of $18.12. That is $2.00 per order too high, and it is presented as complete: the wrong-money-value case that R-16 is meant to stop.
- **Impact:** no UI shows the endpoint yet. UX-8 part b (the Profit tab), the UX-6 Suppliers picks and Discover's best margin will all read it.
- **Fix:** keep only the quotes from the newest freight capture for each `(listing_id, variant_id, quantity, origin_country)`. For example, take the max `captured_at` (or `raw_payload_id`) per group in SQL, then keep the rows of that capture. An older method then either drops out or names a reason.
  - Optionally, when the chosen quote is older than a freshness bound, add a stale flag in `sources.freight` or an estimate label.
- **Test:** quotes A $3.00 and B $5.00 on day 1, then only B $5.00 on day 30. With no method given, the call picks B at $5.00. With `method: "A"`, it reads `freight_missing`.

### XR-17 · low · p2-06 · on Shopify, any bot's Crawl-delay at or past the run budget stops the whole run at that store

- **Where:**
  - `packages/sources/src/pulso_sources/shopify_stores/__init__.py:66-71`: `read_robots` takes the largest Crawl-delay anywhere in the file, from any group (DEC-242 e).
  - `shopify_stores/__init__.py:192-195`: the store's next slot moves out by that delay.
  - `shopify_stores/__init__.py:92-96`: the next request raises `RunDeferred("wall_time_budget")`, which stops the run (`lifecycle.py:327-329`).
  - XR-13's skip is in `listing_images` only (`listing_images/__init__.py:167-174`).
- **Defect:** before p2-06, only PulsoBot's group or `*` counted. Now a delay written for any bot counts. Requests are sequential with in-line sleeps, so one store's long delay ends the run for every store after it in the plan.
- **Failure scenario** (probe):
  1. `first.test` serves `User-agent: SlowBot` / `Crawl-delay: 2000`, past the 1800 s Shopify budget.
  2. The run reads `partial`, `RunDeferred` / `wall_time_budget`, after one request: `first.test/robots.txt`.
  3. `second.test` gets no request, and `first.test/meta.json` is never fetched either.
  4. This repeats every day, because the robots cache only holds stores whose last run succeeded. Every store after `first.test` loses its daily catalog snapshot, and the run's error names the budget, not the store.
- **Smaller case:** a `Crawl-delay: 120` written for some other bot paces that store at 120 s a request instead of 10 s. A 20-page catalog then takes about 42 minutes, past the 30-minute budget.
- **Impact:** it fails closed (fewer requests, never more), but it starves the other stores. `shopify_stores` doesn't run live yet; seed_v1 lists 30 stores.
- **Fix:** take one of these.
  1. **Smallest:** apply XR-13's skip to `shopify_stores`. A store whose next slot is at or past `self.deadline` yields no request, and its target ends `partial` with a log line naming the store.
  2. **Or:** read Crawl-delay only from PulsoBot's group and `*` (fractions included). That keeps DEC-242's fraction fix and drops the "any group" reach, which RFC 9309 doesn't ask for.
- **Test:** store A's robots.txt sets a delay past the budget for another bot. Store B is still fully fetched in the same run.

### XR-18 · low · p2-03 · very large integer filters and cursors answer 500 instead of 422

- **Where:**
  - `apps/api/src/pulso_api/routers/products.py:214`: `category` has `ge=1` but no `le`, and the column is int4.
  - `products.py:215-216`: `price_min` and `price_max` have `ge=0` but no `le`, and they are compared with BIGINT aggregates.
  - `products.py:206`: the `fewest_sellers` cursor is `tuple[int, UUID]` with no bound.
- **Failure scenario** (probe):
  - `GET /v1/products?price_min=1000000000000000000000000000000` → **500**, `DataError` (NumericValueOutOfRange: bigint out of range).
  - `price_max=10^30` gives the same.
  - `category=1099511627776` (2^40) → **500**, integer out of range.
  - `sort=fewest_sellers&cursor=[1e30 as an integer, "<uuid>"]` → **500**.
  - Each one logs a `request_failed` error.
- **Impact:** an authenticated user gets a 500 and an error log line instead of a 422. No data is touched.
- **Fix:** `le=2**63 - 1` on the prices, `le=2**31 - 1` on `category`, and the same bound on the cursor's integer, for example `Annotated[int, Field(ge=0, le=2**63 - 1)]`.
- **Test:** each of the four forms answers 422.

### XR-19 · low · p2-03 · a product whose momentum or store count changes between page loads can repeat, and the web renders the repeat with a duplicate key

- **Where:**
  - `products.py:320-335`: the momentum and fewest-stores keys are live values (the latest feature day; current store matches). The cursor only holds the last row's old key.
  - `apps/web/src/app/(app)/discover/discover.tsx:85`: the pages are concatenated with no de-duplication.
  - The grid's `<li key={item.id}>` (`discover.tsx:158`) and the table's `<tr key={item.id}>` (`feed-views.tsx:248`).
- **Failure scenario:**
  1. The owner scrolls the fewest-stores sort. Page 1 ends at a product P with 0 stores.
  2. The matcher then links a new store listing to a product Q that was already shown on page 1, so Q's count rises from 0 to 1.
  3. The next page, after `(0, P)`, includes Q again among the 1-store products.
  4. Q now appears twice with the same React key: a console warning, and in the virtualized table one row can render over the other.
  5. In the other direction, a product whose key drops past the cursor is skipped until the next refetch. Momentum behaves the same way when the daily feature job writes a new day mid-scroll.
- **Impact:** rare UX glitches. No data is wrong, and a refetch shows the right set. `newest` is immune, because `first_seen_at` never changes.
- **Fix:** de-duplicate by `id` when joining the pages (`discover.tsx:85`), keeping the first occurrence. Accept the rare skip, and add one line to DEC-239 (b) saying keyset over live keys can skip a moved row until the next refetch.
- **Test:** a Vitest of the join: page 2 repeats an id from page 1, and it renders once.

### XR-20 · low · p2-10 · computed money lines have no upper bound: a USD line passes 2^63−1 silently, and a non-USD one answers 500

  - `landed_cost.py:97-100`: `q × C`.
  - `landed_cost.py:112-117`: the fee lines on a price of up to 2^63−1.

### XR-22 · low · p2-06 · an image or JSON answer that isn't content (3xx, 404, a final 5xx) still resets the block count

- **Where:**
  - `packages/sources/src/pulso_sources/framework/lifecycle.py:165-168`: any live answer outside 403/429/430 resets, unless it is robots.txt.
  - DEC-069: "any other live response resets it".
  - DEC-242 (a): it keeps that rule for everything except robots.txt.
- **Failure scenario** (probe, `listing_images`, threshold 2, 4 daily runs):
  - Each run, one image answers 404, 302 or 503 (after its retries), and the next image answers 403.
  - The count goes 0 → 1 every run. The source stays enabled, with `consecutive_block_count = 1`, after 12 requests (24 with the 503 retries).
  - A host that redirects every image to a challenge page never counts at all. Each image fails `http_302` and backs off, so it is asked again each day, up to 1,350 images a host a run.
- **Impact:** a policy gap, not a code slip; p2-06 kept the documented rule. Bot blocks from CDNs typically come as 403 or 429, which count, and an answer that does reset is not a block under DEC-069. So the threshold fails only for blocks that never answer 403/429/430. It fails closed per image: no content is stored.
- **Fix:** this needs a decision. Changing which answers count is a compliance rule (DEC-069, SPEC §4.2), so record it under its own DEC through the lead, not under DEC-248. Options:
  1. Only a 2xx or 304 to a content request resets the count. A 3xx, 404 or 5xx leaves it as it was, as robots.txt now does: one more `resets_blocks`-style check in `_capture`.
  2. Also count a 3xx on an image as a block, since image URLs never legitimately redirect for PulsoBot (redirects aren't followed).
- **Test:** the probe pattern. With option 1, two runs of "404 then 403" disable once at threshold 2.

## Observations (no fix requested)

- **p2-06, XR-15's backslash check is redundant:** the "backslash allowed" revert survives, because no URL can tell it apart from the `@` check. Each backslash form that `urlsplit` maps onto a listed hostname has an `@` in its netloc. Without an `@`, the backslash stays inside `hostname`, which matches no listed host. It is harmless defence in depth, and no test can fail without it.
- **p2-06, re-enable doesn't reset the count:** nothing resets `consecutive_block_count` when the owner re-enables a source (`grep` finds only `lifecycle.py:166-168` and CJ). Before p2-06, the next run's robots.txt 200 reset it. Now it stays at the threshold, so the first block after a re-enable disables the source again at once (count 6). That fails closed. If the owner wants a fresh count on re-enable, the admin PATCH can reset it.
- **p2-06, a robots.txt with no body:** a 2xx robots.txt with an empty body, or an unsolicited 304, reads as allow-all in `listing_images` (`:131, 182`), as RFC 9309 treats an empty file. This predates p2-06.
- **p2-06, 200 challenge pages:** an image answering 200 with an HTML challenge page fails `ImageContentType` inside `fetch`, before the block code runs. It neither counts nor resets, the image backs off, and nothing is stored. This predates p2-06.
- **p2-03, card-level `as_of` and `stale`** (`products.py:418-436`): they use each family's newest capture. The price stats, which can come from an older store snapshot, aren't included. The price numbers carry their own correct `as_of` and `stale`; only the card-wide cue can look fresher than the min price. This is by design (the comment at `:418`).
- **p2-03, which sources count as "feeding"** (`products.py:345-347`): any listing with a product counts, live or delisted, on a merged product or not. DEC-239 (e) says "a live listing on an unmerged product". A source whose only listings are delisted could still show in the degraded banner. This is cosmetic.
- **p2-03, `GET /v1/categories`** is unpaginated. It is bounded by the categories in use (at most the taxonomy, about 5,600), which follows DEC-068's bounded-registry precedent for `GET /sources`.
- **p2-10, `variant_id` without `supplier_listing_id`** answers 404 "Variant not found on this supplier listing." (`landed_cost_loader.py:201-206`). A request-shape error would read better as a 422.
- **p2-10, reference price:** it is the product's lowest live USD store price (`price_min_minor`) even when a specific supplier variant is costed. That is conservative, and it is labelled with its listing's trace.
- **p2-10, freight history:** `freight_quotes` loads every historical quote row for the listing at that quantity (`:113-135`). Unbounded history per call is cheap today, and `ix_shipping_options_listing_id_captured_at` exists. XR-16's fix reads only the newest capture anyway.
