## The exact freight rule (DEC-250 a, b)

```sql
SELECT … FROM (
  SELECT shipping_options.*, sources.key,
         rank() OVER (
           PARTITION BY coalesce(variant_id, :single_live_variant_or_null), origin_country
           ORDER BY captured_at DESC, raw_payload_id DESC
         ) AS capture
  FROM shipping_options JOIN raw_payloads … JOIN sources …
  WHERE listing_id = :listing AND destination_country = 'US' AND quantity = :q
) newest
WHERE capture = 1 [AND method = :method]
ORDER BY id DESC
```

- **Newest capture:** `rank() = 1` keeps every row of the newest capture in each partition: the newest `captured_at`, and on a tie the later `raw_payload_id`. CJ writes one row per returned method per capture (`cj/tracked.py:196-211`), so this is exactly the method set of the newest response.
- **Partition key:** `variant_id` and `origin_country`. On a single-variant listing, a null-variant quote counts as the variant's (`coalesce`), because DEC-246 (d) treats the two as one freight question. With two separate "newest" captures, an older null-variant method could win again. On a multi-variant listing, the second `coalesce` argument is NULL, so the key is `variant_id` itself.
- **Method:** a requested method is filtered **after** the ranking. Filtering it first would make the method's own last capture the newest, which is the XR-16 bug.
- **After the query:** DEC-246 (d)'s rules apply unchanged. The variant fit decides between a null-variant quote and the variant's own. A capture holds one row per method; a re-parse keeps the newest parse (`id DESC`). Without a method, the cheapest in USD wins.
- **Gap codes:** if the newest captures hold no fitting row, the code is `freight_missing`. A requested method that only older captures listed also reads `freight_missing`. If another variant's newest capture still lists the method, the code is `freight_variant_mismatch`, as before.
- **Bounded and index-friendly:** the query reads one listing's rows through an index on `listing_id`. Postgres pushes `rank() <= 1` into the window as a `Run Condition`, so each partition stops at its first capture, and only the newest capture's rows come back. Plan on the throwaway DB (`enable_seqscan = off`, empty tables):

  ```
  Sort (anon_1.id DESC)
    -> Subquery Scan on anon_1   Filter: (capture = 1)
      -> WindowAgg   Run Condition: (rank() OVER w1 <= 1)
        -> Sort (COALESCE(variant_id), origin_country, captured_at DESC, raw_payload_id DESC)
          -> Nested Loop
            -> Index Scan using uq_shipping_options_listing_id_variant_id_origin_countr_d1f6
                 Index Cond: (listing_id = 1 AND destination_country = 'US' AND quantity = 1)
            -> Index Scan using pk_raw_payloads / pk_sources
  ```

- **No freshness flag (DEC-250 f).** `sources.freight.as_of` already carries the chosen quote's capture time. The stale cue belongs to the Profit tab.

## XR-20 and XR-21 (DEC-250 c–e)

- **Bound:** `pulso_core.landed_cost.BIGINT = 2**63 - 1`, the column type and the request bound in DEC-246 (g).
  - **Checked:** goods, freight, duty (it can pass 100%), landed cost, the payment fee (`bps × price + fixed` reaches about 2^64 inside the request bounds), the margin and `margin_bps` (`margin × 10000 / price`).
  - **Not checked:** the Shopify fee and returns. Both are at most the price, because their bps are 0..10000 at the API and by the settings check constraints.
- **Out-of-range value:** it becomes null and adds `amount_out_of_range`. Every total that needs it stays null. A new line, `if missing: margin = margin_bps = None`, keeps R-16's "only a complete row has a margin" even when `margin_bps` alone is out of range.
- **Non-USD:** `convert_minor` raises `ValueError` past BIGINT, before or after converting. `landed_cost()` names that `amount_out_of_range`, and `cheapest()` sorts it last, like a quote without FX. Before this change, both paths answered 500.
- **Why a code and not a 422:** one absurd supplier row would otherwise fail the whole best-supplier pick, and the endpoint keeps a single answer shape. Adding the code extends DEC-246 (c)'s list; it changes none of its rules.
- **Order:** `missing = tuple(sorted(set(missing), key=MISSING.index))`. `MISSING` is DEC-246 (c)'s order, then `amount_out_of_range`. An unknown code raises an error instead of vanishing. The API's `Missing` literal gained the code, and a test checks `get_args(Missing) == MISSING`.
- **DDP:** `estimates` drops `duty_bps` and `customs_fee_minor` when `ddp` is true (in the pure function). The loader drops both from `sources` under DDP, whether they came from an override or from settings.
- **Conflict check against DEC-246:** neither fix changes a DEC-246 rule. The order fix makes the code match DEC-246 (c). The DDP fix narrows (c)'s "overrides are listed in estimates" to overrides that feed the result, which follows from (b): DDP zeroes duty and the customs fee. DEC-250 (e) records the narrowing.
