## imp-108 · `ed76039` · clear

**Rules (AGENTS.md §3, DEC-051):** "`to_minor` … rejects fractional minor units, nonfinite values, floats and BIGINT overflow, and never silently rounds."

- **`to_minor` guards** (`packages/core/src/pulso_core/money.py:26-29`):
  - `value.adjusted() + exponent` is the power of ten of the leading digit **in minor units**.
  - Above 18, the amount is at least 10^19 minor units, which is more than 2^63 − 1, so the BIGINT error is right.
  - Below 0, a non-zero amount is smaller than one minor unit, so the fractional error is right.
  - A valid amount has 1 ≤ |minor| < 2^63, so the sum is between 0 and 18 and neither guard fires.
  - The scaling after the guards is unchanged and exact: `prec` ≥ digits + exponent + 1 covers the coefficient growth from multiplying by `10**exponent`. The bounded sum also keeps the product inside `Emax`/`Emin`.
- **Boundaries:** −2^63 is still accepted and ±(2^63) is still rejected. The existing `test_to_minor_rejects_one_minor_unit_outside_bigint` pins this for USD, JPY and KWD.
- **0 and 3 minor digits:** a sub-yen JPY amount and a sub-fils KWD amount raise the fractional error. Both guards use the per-currency exponent.
- **Negative and zero:** the guards ignore sign. `-0` and zero at any exponent still return 0, pinned by the new zero cases. The CSV non-negative check (`packages/sources/src/pulso_sources/imports/csv.py:68`) now gets the fractional error for `-1e-1000030`, where it used to get 0.
- **No float:** the `TypeError` for `float`/`bool` is unchanged.
- **Rounding direction:**
  - `to_minor` never rounds.
  - `convert_minor` rounds once. The multiply is exact, because `prec` ≥ amount digits + rate digits + 6.
  - For CSV-valid rates, the divide keeps enough digits that neither the context rounding nor a double rounding can change the result. The probe found 0 mismatches against exact rational rounding.
- **Overflow:**
  - `convert_minor` maps `InvalidOperation` (quantize past `prec`) and `Overflow` (past `Emax`) to the BIGINT `ValueError`. Both need at least 10^25 minor units.
  - The only signal left is the documented `Underflow` ceiling (a rate below about 10^−1,000,000). It is unreachable: the CSV `rate` column needs a rate of at least 10^−8 (`imports/csv.py:59-63`), and `convert_minor` has no production caller. Only `packages/core/tests/test_money.py` and `packages/sources/tests/fx_frankfurter/test_fx.py` call it.
- **Callers on `origin/main`** (every import of `pulso_core.money`):
  - `imports/csv.py:68` (`_cell`): `except ValueError, KeyError, InvalidOperation` (`:225`) turns any money error into the row error `Invalid money value`. This is the fixed path; a `1e1000000` cell used to answer 500.
  - `cj/csv.py:81, 173`: commit re-runs `to_minor` on rows that preview already accepted with the same currency. A `ValueError` fails the run closed, because `framework/lifecycle.py:318` catches `Exception`.
  - `cj/__init__.py:91`: `InvalidOperation` is mapped to `ValueError`. The new `ValueError`s propagate and fail the run closed. Before, an `Overflow` escaped as an `ArithmeticError`, which also failed the run.
  - `cj/tracked.py:161, 205, 241`: money arrives as `Decimal`, through `json.loads(parse_float=Decimal)` and the `Money` type (`ge=0`, finite). A `ValueError` fails the run closed.
  - `shopify_stores/records.py:154, 206-207`: the same; a `ValueError` fails the run closed.
  - `shopify_stores/variants.py:68`: `from_minor` of a `StrictInt` up to 2^63 − 1 is exact (19 digits at most, under `prec` 28). The JPY `to_minor` then rejects a non-whole yen amount.
  - Importers that use only `CURRENCY_EXPONENTS` are unaffected: `fx_frankfurter/__init__.py`, `shopify_stores/imports.py` and `test_schema_integration.py`.
- **Siblings:** no other module scales money. Outside `money.py`, `quantize`, `scaleb` and `localcontext` appear only in the CSV rate check (`imports/csv.py:63`). A rate below 10^10 has at most 18 digits there, so quantize can't signal.

## imp-109 · `c494d05` · findings: XR-5 low, XR-6 low

**Rule (DEC-051):** "JWTs require iss/exp/nbf/iat/sub/azp, RS256, five-second leeway and the admin allowlist. JWKS sets expire after 300 seconds."

Clear apart from XR-5 and XR-6:

- **Claims** (`apps/api/src/pulso_api/auth.py:39-46`):
  - `require` lists all six claims. PyJWT treats a null value as missing.
  - `leeway=5` applies to `exp`, `nbf` and `iat`. In PyJWT 2.15.1, `iat` must be an integer, and a future `iat` is rejected.
  - The new no-`exp` and no-`iat` cases kill mutant A.
- **Issuer:** PyJWT compares `iss` to a `str` issuer by equality, and `iss` must be a string. No substring match is possible.
- **Audience and authorized party:**
  - `azp` is checked for membership in a `list[str]` (`CommaList`, `packages/core/src/pulso_core/settings.py:22, 45`). That is exact, not a substring match.
  - No `audience` is configured, so PyJWT rejects any token that carries `aud` (401, fails closed). Clerk session tokens carry no `aud` by default.
- **Algorithm:** `algorithms=["RS256"]` against the JWK's raw `.key`. `none`, HS256 key confusion and ES256 all answer 401 (`test_wrong_algorithm_rejected`).
- **Rotation and `kid` miss:**
  - `PyJWKClient(lifespan=300, timeout=3)`.
  - An unknown `kid` forces one refresh, unless a successful fetch happened in the last 30 s (PyJWT's default `cooldown_duration`). So a just-rotated Clerk key can answer 401 for up to 30 s.
  - A removed key stays valid for up to 300 s, which DEC-051 accepted. That isn't a finding.
  - An empty or unusable key set is never cached: `JWKSetCache.put` raises first.
- **503 vs 401:**
  - Unset issuer or JWKS URL → 503 `auth_unconfigured`.
  - `URLError`, `TimeoutError`, `HTTPException`, an HTML body or a non-UTF-8 body → 503 `auth_unavailable`.
  - JSON that isn't a key set → 401. This is imp-109's documented ceiling, and I agree it's a status-code decision.
  - A bad token never reaches the 503 branch, because the header read and `jwt.decode` raise only `PyJWTError`s.
  - The gap left is XR-5.
- **Nothing echoed:**
  - The `APIError` handler returns fixed details and doesn't log the cause.
  - The request log line records the path only (`main.py:51`).
  - `PyJWKClientError` messages contain the token's `kid`, but they are never logged or returned.
  - The 500 path logs a traceback. For XR-5, that traceback holds only the socket error text.
- **No fail-open path:**
  - Every route depends on `current_principal`.
  - `apps/api/src` has no auth bypass.
  - `provision_principal` runs only after `verify_token` returns.
  - An empty `clerk_authorized_parties` → 401, and an empty allowlist → 403.
  - Every unexpected exception → 500.
- **Tests:**
  - The revert reproduces the report's red run (HTML and Latin-1 bodies → 500).
  - The unknown-`kid`, unconfigured and `{"keys": []}` cases pin behaviour that was already right, as the report says.
  - `test_jwks_fetch_failures` runs the real `fetch_data` with only `OpenerDirector.open` replaced, and clears the `jwks_client` cache before and after. That isolation is sound.

## Findings

### XR-5 · low · imp-109 · a connection reset or TLS error while reading the JWKS body still answers 500, not 503

- **Where:** `apps/api/src/pulso_api/auth.py:48`.
- **Defect:**
  - PyJWT 2.15.1's `fetch_data` wraps only `URLError`, `TimeoutError` and `http.client.HTTPException` around `opener.open(...)` and `json.load(response)`.
  - A `ConnectionResetError` or `ssl.SSLError` raised by the socket while the body is read is a bare `OSError`. It escapes both PyJWT's wrapper and the new `except` tuple.
  - The comment "PyJWT wraps only network errors" claims more than PyJWT does.
- **Failure scenario:**
  1. The cached key set expires (every 300 s), so the next request fetches it again.
  2. The connection resets after the headers arrive, for example from a proxy restart, a Wi-Fi drop on the owner's PC or an egress blip on Railway.
  3. The request answers 500 `internal_error` and logs a `request_failed` traceback, not 503 `auth_unavailable`.
  4. The probe confirmed it: `ConnectionResetError` and `ssl.SSLError` on the body read both escape, and `TimeoutError` answers 503.
- **Impact:** it fails closed. The cost is the web app's generic error in place of the auth-unavailable state, and an internal-error log line for an outage.
- **Fix:**
  - Add `OSError` to the 503 tuple at `auth.py:48`. Only the key fetch can raise it, because the unverified header read and `jwt.decode` do no I/O. `URLError` and `TimeoutError` are `OSError`s already.
  - Correct the comment.
  - Add a `test_jwks_fetch_failures` case (`apps/api/tests/test_api.py:240-248`) whose opener returns a body whose `read()` raises `ConnectionResetError`, expecting 503 `auth_unavailable` and no provisioning.

### XR-6 · low · imp-109 · during a JWKS outage, concurrent requests wait their turn for one fetch at a time

- **Where:** `apps/api/src/pulso_api/auth.py:31` (`PyJWKClient(..., timeout=3)`) and `:38` (`get_signing_key_from_jwt`).
- **Defect:**
  - PyJWT's `get_signing_key` holds the client's `RLock` across the network fetch.
  - A failed fetch caches nothing.
  - So while the endpoint is down, every request repeats the fetch, one after another.
  - The imp-109 report says this is "bounded by the 3-second timeout", which holds only for one request at a time. Also, urllib applies the timeout per socket operation, and name resolution has no timeout at all.
- **Failure scenario:**
  1. Clerk's JWKS endpoint stops answering.
  2. A page load fires 6 API calls in parallel.
  3. The nth call answers 503 after about n × 3 s, so the 6th waits about 18 s. Each waiting call holds a threadpool worker that long.
  4. The probe confirmed it: 5 concurrent verifications with a 1 s failing fetch answered at 1, 2, 3, 4 and 5 s.
- **Impact:** it fails closed (503). The cost is UX and threadpool slots, with one user in v1.
- **Fix:** in `verify_token`, keep the monotonic time of the last fetch failure (`PyJWKClientConnectionError`, plus `OSError` after XR-5) and, for the next 5 s, raise the 503 without calling the client. Test it with the existing opener patch counting calls: two back-to-back requests during an outage → one fetch, both 503. If the code isn't wanted, correct the ceiling text in the [[Auth]] note instead.
