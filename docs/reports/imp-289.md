# imp-289 — Profit's default supplier pick follows the in-stock rule Best margin uses

## The bug

Without `supplier_listing_id`, `POST /v1/profit/calc` (`landed_cost_loader.calculate()`) costed every live supplier listing and took `best()` over all of them. The Suppliers tab's Best margin pick takes `best()` over in-stock rows only (DEC-264 b, DEC-243's rule). So when the best complete margin belonged to a known out-of-stock listing, Profit's default costed a supplier that Suppliers never picks. Reproduced before the fix: the default calc answered listing 2 (sold out) where Best margin was listing 4.

## What changed

- **One predicate** (`packages/core/src/pulso_core/landed_cost_loader.py`): `in_stock(available, stock)` is DEC-243's rule, and `stocked(session, listing_id)` applies it to the listing's latest snapshot, read the way the Suppliers tab reads it (`captured_at`, then `id`, newest first). With no snapshot, the listing isn't known to be out of stock. The two copies of the expression, in `routers/product_suppliers.py` (row `in_stock`) and `routers/products.py` (Overview best supplier cost), now call it. One line each.
- **The default pick** (`calculate()`): in-stock listings first. The pool is the listings not known to be out of stock, or every listing when none is in stock. DEC-246 (f) runs unchanged inside the pool: `best()`, else the fewest missing inputs, then the lowest id.
- **Fallback (decided):** with nothing in stock, the same rule runs over the out-of-stock listings, so the page still shows the best out-of-stock margin. While any listing is in stock, a complete out-of-stock one never beats it, even when the in-stock one is incomplete. Suppliers then shows no Best margin pick either.
- **An explicit `supplier_listing_id`** is costed whatever its stock, as before. Suppliers' rows rely on it.
- **Discover's view** (`0013_economics_in_stock_first.py`, view only): `workspace_product_economics` copies the default pick in SQL, and DEC-265's parity check holds it to the loader. The migration replaces the view with 0010's text plus two edits, read from 0010's file and asserted to apply exactly once:
  - a lateral for the latest snapshot's `available IS FALSE OR stock <= 0`;
  - that flag as the pick's first sort key after "has a listing".

  A null flag sorts as in stock. Downgrade restores 0010's view. No table, row or data changes.
- **No API shape change**, so no `pnpm gen:api`. The response doesn't flag an out-of-stock default yet (backlog row 1).

## Can the picks still disagree? (DEC-264 is the source of truth)

| Case | Suppliers Best margin | Profit default (and Discover) | Result |
|---|---|---|---|
| Best complete listing sold out (`stock=0` or `available=false`) | next in-stock complete | same | Fixed, tested |
| Latest snapshot restocked after a sold-out one (capture tie, later id) | in stock | in stock | Same read order, tested |
| Listing with no snapshot, or no stock fields | in stock | in stock | Tested |
| Delisted listing | excluded (`delisted_at` null) | excluded | Same filter |
| Listing without a supplier | excluded (inner join on `suppliers`) | excluded (`supplier_id` not null) | Same set |
| Margin tie | lowest id (insertion order into `best()`) | lowest id | Same |
| Variants | listing snapshot, no variant | default has no variant (a variant needs `supplier_listing_id`) | Same; variant stock isn't read by either |
| Nothing in stock | no pick | best out-of-stock listing | By design (fallback) |
| In stock but incomplete vs complete sold out | no pick | the in-stock incomplete one | By design: never a known sold-out supplier while one in stock exists |
