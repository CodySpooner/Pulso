## Behaviour (DEC-330)

The operation id is the function name.

| Endpoint | Operation id | Behaviour |
|---|---|---|
| `GET /v1/alerts?unread=&type=&cursor=&limit=` | `list_alerts` | The workspace's unarchived alerts, newest first by `(fired_at DESC, id DESC)`. Keyset cursor `[fired_at, id]`; a bad cursor is 422 `invalid_cursor`. `limit` is 1–100 (default 50). `unread=true` lists unread alerts, `unread=false` read ones. `type` is an exact match (≤ 40 characters). Items: `id`, `rule_id`, `type`, `entity_type`, `entity_id`, `fired_at`, `payload`, `read_at` |
| `GET /v1/alerts/unread-count` | `count_unread_alerts` | `{count}` of alerts that are unread and unarchived |
| `POST /v1/alerts/read` | `read_alerts` | Exactly one of `{ids: [...]}` or `{all: true}`, otherwise 422. Sets `read_at = now()` only where it is null, so the first read time stays. Returns `{count}` |
| `POST /v1/alerts/archive` | `archive_alerts` | `{ids: [...]}`. Sets `archived_at = now()` where it is null, which hides the alert from the list and the count. Returns `{count}` |

- `ids` takes 1–500 bigints.
- An id that is unknown, already in that state, or belongs to another workspace is skipped silently. Every query filters on `workspace_id`.
- The list query is served by migration 0021's `(workspace_id, fired_at, id)` index, scanned backward.
- The count reads the workspace's alerts through the same index. A partial unread index would need a migration, so it's a backlog row.

**Acceptance (brief (a)), test by test.** All of these are in `test_inbox_pages_filters_reads_and_archives`:
- **Keyset order and cursor:** A's alerts list as a4, a3, a2, a1. a4 and a3 fire at the same instant, so a4 comes first by the higher id. A 2-row page returns [a4, a3], and its cursor returns [a2, a1]. A walk one row per page returns all four exactly once, so the cursor between a4 and a3 breaks the tie on id. `cursor=nope` is 422 `invalid_cursor`.
- **Unread filter:** after a1 is read, `?unread=true` gives [a4, a3, a2] and `?unread=false` gives [a1]. After a2 is archived, `?unread=true` gives [a4, a3].
- **Read by ids and all:** `{ids: [a1, b1]}` returns count 3 (B's id is skipped). `{all: true}` returns 0. Afterwards a1 still has the `read_at` from its first read. The bodies `{}`, `{ids, all}`, `{all: false}` and `{ids: []}` are 422.
- **Archive hides from the list and the count:** `{ids: [a2, b1]}` returns count 2. The list becomes [a4, a3, a1]. `{ids: []}` is 422.
- **Two-workspace isolation:** A never lists b1. A's reads, `all: true` and archive never touch b1. B still lists [b1] with unread count 1.

**Mutations.** A scratch script applied each one-line change to the router, ran `test_alerts.py`, and restored the file:
- **Killed (11):**
  1. archived alerts listed;
  2. the list crosses workspaces;
  3. the cursor compares `fired_at` alone;
  4. the unread filter inverted;
  5. the count includes archived alerts;
  6. read overwrites `read_at`;
  7. read crosses workspaces;
  8. archive crosses workspaces;
  9. archive ignores `ids`;
  10. read ignores `ids`;
  11. the body validator accepts `ids` with `all`.
- **Survived (1): `id` dropped from ORDER BY** (`order_by(fired_at.desc())` only). Postgres still returned the tied pair in id order: the backward scan of `(workspace_id, fired_at, id)` produces that order anyway. Nothing short of forcing a different plan would expose it. The cursor comparison itself is covered by mutation 3.
