### p2-16 ranking, escaping and threshold · clear

- **Kinds:** `kind` is `lower(text) = lower(q)`, then `ILIKE q || '%'`, then `ILIKE '%' || q || '%'`, then fuzzy. `DISTINCT ON (key)` keeps each entity's best candidate, ordered by kind, then `word_similarity` descending, then priority (a product title beats a listing title), then length.
- **Fuzzy:** `col %> q` is `word_similarity(q, col)` over the 0.6 threshold, the same function that ranks. It starts at 3 characters. A query with no word characters (such as `---`) has no trigrams and matches nothing by fuzzy, only by substring.
- **Escaping:** SQLAlchemy renders `ILIKE … ESCAPE '/'` and escapes `%`, `_` and `/`. With an explicit escape character, a backslash is literal. Probe:
  - `k\s` finds `back\slash.example.test`, and `a/s` finds `sla/sh.example.test`;
  - `\\`, `//`, `\%` and `/%` find nothing;
  - p2-16's own test covers `%_`.
- **Index use:** both the `ILIKE` and the `%>` branches can use `gin_trgm_ops`. p2-16's timing test measured it.

### p2-19 GS1 validation and GTIN-14 normalisation · clear

- **Format:** only `[\s-]` is stripped, and only 8 or 12–14 ASCII `[0-9]` digits pass. Unicode digits fail.
- **Check digit:** after `zfill(14)`, the weights run 3, 1, 3, … from the digit left of the check digit, and `-sum % 10` must equal it. That is GS1 mod-10. UPC-A `036000291452` and EAN-13 `0036000291452` both give `00036000291452`.
- **RCNs:**
  - for GTIN-14, GS1 prefix = `code[1:4]`: 200–299 (`code[1] == "2"`), 020–029 and 040–049;
  - for GTIN-8 (`000000` + 8), the GS1-8 prefixes 0 and 2.
  - A UPC-A with number system 2 or 4 pads to `002…` / `004…`, so it is caught too.
- **Placeholders:** all one digit, or a ±1 run (with 9→0 wrap) after the leading zeros. A real code is never that regular.
- **Not caught (fine):** coupon prefixes (05x, 98x–99x) aren't products, so a link through one is very unlikely.

### p2-19 the 1.0 link goes through M-3's rules; idempotent re-runs · XR-34, XR-35 low

- **Rules:** each pair goes through `link()`. Only product-less listings move. There is one `algo` / `link` decision per moved listing, with `candidate_id`, confidence 1.0000 and reason `gtin-1: GTIN <14>`, in the same transaction as the pointer. The candidate becomes `accepted`.
  - Decided pairs are skipped.
  - A manual latest move blocks the move.
  - `vetoed()` stops a third-listing join.
  - `apart()` (p2-21) stops split pairs.
- **Re-runs:** a pair already on one product is skipped. A two-product `pending` row is re-set to the same `Decimal(1)` / `gtin-1`, which the ORM doesn't write, and `link()` returns False. p2-19's tests compare every row before and after a second run.
- **Vendor rule:** a vendor's reused code drops that vendor. A store–store or store–supplier pair across vendors links. A vendorless listing is its own vendor, but no test fails without that (XR-35).
- **Finding:** a pending `gtin-1` row outlives its GTIN (XR-34).

### p2-21 the matching lock · deadlocks, release and scope clear; XR-35

- **Order:** every matching writer takes `pg_advisory_xact_lock(0x50554C534D415443)` before any row lock:
  - the score pass as its first statement (`matcher.py:158`);
  - the GTIN pass before each pair (`:271`). The first GTIN transaction runs only SELECTs before it;
  - each service call first (`decisions.py:32, 74, 115, 143`).

  So two matching writers can't deadlock: the second waits on the advisory lock while holding no row lock.
- **Release:** transaction-scoped, so it is released at commit or rollback. The matcher re-takes it each transaction. On an error, the session's rollback releases it (`get_db` closes the session, and the pool rolls back on return). It is never held across a commit.
- **The two-int keys:** the single bigint key can't collide with the workers' two-int Beat and source locks (different lock spaces).
- **Collectors:** they don't take the lock. `link()`'s `FOR UPDATE` on two listings against a multi-listing CSV import is the pre-existing p2-13 row-lock order (observation).
- **Finding:** the lock test covers only `split()`. Removing the lock from either matcher pass passes every test (XR-35).

## Findings

### XR-29 · medium · p2-21 · `membership(t)` replays by `decided_at`, the transaction's start, which can disagree with the order moves took the lock

- **Where:**
  - `packages/ml/src/pulso_ml/matching/decisions.py:158-166`: `DISTINCT ON (listing_id) … ORDER BY listing_id, decided_at DESC, id DESC`.
  - `packages/ml/src/pulso_ml/matching/matcher.py:438-443`: `manual()`, same order.
  - `packages/core/src/pulso_core/models/catalog.py:234`: `decided_at` is `server_default now()`, the transaction's start time, not the insert's.
  - `apps/api/src/pulso_api/auth.py:115-126`: `current_principal` queries the request's session (`provision_principal`). So a UX-1 request's transaction starts before its service call takes the lock.
  - `matcher.py:135-142`: the first matcher transaction starts with the count query and `redirects()`, before the first GTIN pair's lock.
- **Defect:** the one lock orders the moves. Every decision is inserted after its writer takes the lock, so `id` follows that order. But replay sorts by `decided_at` first. A transaction that started earlier but took the lock later writes a later move with an earlier stamp, and replay reads its older row as the latest.
- **Failure scenario** (`test_xr29_replay_follows_the_order_moves_took_the_lock`, from the probe):
  1. The owner's request opens its transaction at 06:06:54.027 (the auth query).
  2. Meanwhile the matcher links product-less listings A and B onto a new product N and commits. A's row: `algo`/`link`, `decided_at` 06:06:54.079, id 1.
  3. The owner's `merge(N into P)` now takes the lock and moves A and B to P. A's row: `owner`/`merge`, `decided_at` 06:06:54.027, id 3.
  4. `listings.product_id` is P, but `membership(now)[A]` is **N**, the merged product. It stays N for every later t, until A's next decision.
- **Impact:**
  - **Today:** nothing reads `membership(t)` yet, the service has no endpoint, and no `ml` consumer runs.
  - **Once UX-1 and imp-226 land:** any owner click during a matcher run can hit it. DEC-257 (g) makes `membership(t)` the only grouping for features, so features silently group the listing with the wrong product, and the leakage test can't see it. `manual()` misreads the same way. It is harmless today, because only listings already on a product are affected, and the matcher never moves those.
- **Fix:**
  - **Order the replay by `id`:** `ORDER BY listing_id, id DESC` in `membership()`, and `ORDER BY id DESC` in `manual()`. Keep the cutoff on `decided_at`; its fuzz is at most one transaction's length. Because every writer inserts under the one lock, `id` order is the order the moves happened, so this also reads every row already written correctly.
  - **Not:** stamping `clock_timestamp()` at insert would fix new rows only.
  - **Record it** as a refinement of DEC-257 (e) in the fix PR.
- **Test:** `test_xr29_replay_follows_the_order_moves_took_the_lock` in `packages/ml/tests/test_matcher.py`, marked `xfail(strict=True)`.
  - With `membership()` ordered by `id`, it XPASSes, and the other 17 matcher tests still pass (checked, then reverted).
  - The fix removes the mark.

### XR-30 · low · p2-21 · a merge that lands mid-run hides a split's cannot-link, and the split pair is queued for good

- **Where:**
  - `matcher.py:141`: `redirects()` is loaded once per run.
  - `matcher.py:408-430`: `apart()` resolves the other listing's group through that map.
  - `matcher.py:193-194`: `apart()` skips the pair before the candidate lookup, so a row it once let through is never revisited.
  - `matcher.py:88-95`: the `lock()` docstring's guarantee covers pointers, not the map.
- **Failure scenario** (probe):
  1. The owner splits S off P onto a new product N. Y sits on Q, at the queue angle (image 0.8).
  2. The run loads its redirects. Then an owner `merge(P into Q)` commits.
  3. The score pass reads Y's group as just Q (stale map). S's split from P isn't seen, so the S–Y pair is written as `pending` 0.8300 (two products).
  4. The next run reads a fresh map, and `apart()` is now true. It skips the pair, which stays `pending` 0.8300.
- **Impact:** the queue (UX-1) keeps suggesting a pair the owner split, and an accept merges N with Q, undoing the split. It needs an owner merge during a run, and it never auto-links.
- **Fix:**
  - Reload `redirects()` after taking the lock in each matcher transaction (one query over merged products), or resolve `from_product_id` through `merged_into_id` in `apart()`'s SQL.
  - Optionally, when `apart()` finds a pending row, mark it `split`, as `split()` does.
- **Test:** the probe (it monkeypatches `gtins` to commit the owner merge after `redirects()`).
