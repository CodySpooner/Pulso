## Which values now raise, and why

`value.adjusted()` is the power of ten of the amount's leading digit, so `adjusted() + exponent` is the power of ten of the leading digit **in minor units**.

- **`> 18`:** the amount is at least 10^19 minor units, and 10^19 > 2^63. It can never fit BIGINT, so it raises the BIGINT error before any arithmetic. Without this check, an exponent near 10^6 overflowed the default context (`Emax` 999999) and escaped as `decimal.Overflow`. That is neither a `ValueError` nor an `InvalidOperation`, so the preview answered 500.
- **`< 0`:** a non-zero amount below one minor unit has fractional minor units. Without this check, an exponent below about −10^6 underflowed to `0` (`Underflow` isn't trapped by default), passed the integral check and returned `0`. A negative such amount also passed the CSV non-negative check.
- **Zero** skips both checks (`if value`). At any exponent it still returns 0; the new zero cases pin that.
- **`convert_minor`:** the inputs are already validated (an integer amount, and a finite positive `Decimal` rate), and the quantize exponent is between −3 and 0. So the step can signal only two things. `Overflow` comes from a product or quotient past `Emax`. `InvalidOperation` comes from quantize when the result needs more than `prec` (≥ 28) digits, which means at least 10^25 minor units. Both are beyond BIGINT, so the documented BIGINT error is accurate. Today `convert_minor` has no production caller; only tests use it.

## Why rounding is unchanged for valid amounts

A valid amount gives an integer `scaled` with 1 ≤ |scaled| ≤ 2^63 < 10^19. So `adjusted(scaled)` is between 0 and 18, and `adjusted(scaled) = adjusted(value) + exponent`. Neither new check can fire for a valid amount. After the checks, the code is the same as before: same precision, same multiply, same integral and BIGINT checks. In `convert_minor`, the `try` wraps the same expression with the same rounding, and only exception paths changed.

**Differential check (scratchpad only, not committed).** I compared `origin/main`'s `to_minor` with the branch on 300,000 random amounts: 1–25 digits, both signs, every currency, and exponents in ±30, ±1,000,040 and −1,000,060…−1,000,020. Both versions gave the same result for 251,582 inputs, including every input the old code accepted with a non-zero result. The other 48,418 inputs differ as follows:

| Before | After | Count |
|---|---|---|
| `0` for a non-zero amount | `ValueError` "fractional minor units" | 47,520 |
| `decimal.Overflow` | `ValueError` "exceeds BIGINT range" | 3 |
| `ValueError` "fractional minor units" | `ValueError` "exceeds BIGINT range" | 895 |

The last row covers amounts that are **both** too large for BIGINT and fractional, such as `92233720368547758080.001` USD. The size check now runs first. Both versions raise `ValueError`, and the CSV row error is the same `Invalid money value`. No existing test pins that message for such a value.

## Known ceilings (not changed)

- **`convert_minor` with an absurdly small rate.** Below about 10^−1,000,000, the product underflows and rounds with the context's `ROUND_HALF_EVEN`, not the requested `rounding`. So `ROUND_UP` gives 0, not 1 minor unit. It is unreachable today: the CSV `rate` column needs a rate of at least 10^−8 (`csv.py:61-63`), and `convert_minor` has no production caller. Fix it when needed by trapping `Underflow` in that `localcontext` and raising `ValueError`.
- **Strings `Decimal` can't parse.** `to_minor("abc", …)`, or an exponent past `Decimal`'s own limit (about 10^18), still raises `InvalidOperation` from `Decimal(amount)`. `_cell` parses with `Decimal(value)` first, and `parse_csv` already catches `InvalidOperation` (`csv.py:223`), so an import gets a row error. That behaviour is outside F-14 and was left alone.
