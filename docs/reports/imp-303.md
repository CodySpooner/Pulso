## Changes (`apps/api/tests/test_products.py`, +16 −5)

1. **imp-303:** a new autouse `clock` fixture points the products router's `datetime.now` at the module's `NOW` (`monkeypatch.setattr("pulso_api.routers.products.datetime", Mock(wraps=datetime))`, with `now.return_value = NOW`). The server and the fixtures now read the same instant. `age_days == 9` is therefore exact at any time of day, across 00:00Z, and however long ago the module was imported. The assertion itself is unchanged.
2. **Same pattern, also fixed:** `test_overview_stats_match_sql_spot_checks` compared the API's age (the router's clock) with `SPOT_CHECK`'s `(now() AT TIME ZONE 'UTC')::date` (Postgres's clock), read on a later call. The SQL now takes `CAST(:today AS date)` bound to `NOW.date()`, so both sides use one date. Before this change, the window was the milliseconds between the API call and the query. With the pin and without this change, the window would grow to the whole time since import (see mutation M-a).
3. **imp-304:** `body.as_of > NOW - 5 min` became `> datetime.now(UTC) - 5 min`, a timestamp taken inside the test. `as_of` is the newest raw payload's `captured_at`, which Postgres sets (`server_default=func.now()`) when the fixture seeds it.

### imp-304 behaves differently from the backlog row's description

A long suite doesn't break the old check. `captured_at` is written after the import, so `as_of − NOW` is the elapsed time, which is ≥ 0, and the check only gets looser as the suite runs. `NOW` shifted 10 minutes into the past passes before and after the fix. The old check failed only when `NOW` was more than 5 minutes ahead of Postgres's clock. That happens when `NOW` is pinned to check a time of day (imp-301 had to keep its pinned dates in the past for this reason), or when the DB container's clock lags the host. The `+6m` row below reproduces it: main fails, the fix passes.

## Determinism: times checked

A scratch pytest plugin (session scratchpad, not committed) sets `test_products.NOW` in `pytest_collection_modifyitems`, before any fixture runs:

```python
import os
from datetime import UTC, datetime, timedelta


def pytest_collection_modifyitems(items):
    value = os.environ.get("PIN_NOW")
    if not value:
        return
    pinned = (
        datetime.now(UTC) + timedelta(minutes=int(value[:-1]))
        if value.endswith("m")
        else datetime.fromisoformat(value)
    )
    for module in {i.module for i in items if i.module.__name__.endswith("test_products")}:
        module.NOW = pinned
```

```sh
# Git Bash, from the worktree root; pin_now.py on PYTHONPATH
PIN_NOW=2026-10-24T23:59:30+00:00 uv run pytest -p pin_now -q -p no:cacheprovider -rf apps/api/tests/test_products.py
```

The real clock read 2026-10-25 10:5xZ. With the clock fixture in place, the server reads the pinned `NOW`. Without it (main), the server reads the real clock, so `NOW = 23:59:30Z yesterday` is a run that imported before midnight and reached the tests after it.

Pinned dates stay at or before the real date, as in imp-301. A `NOW` on a later UTC date than the real clock would make the velocity family's `as_of` its `computed_at`, which comes from Postgres's clock. That can't happen in a real run, where `NOW` is the import time.
