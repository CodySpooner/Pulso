## 1. First-load CLS at 1440 (`loading-stability.spec.ts`)

### What shifts

`PerformanceObserver` layout-shift `sources` (a diagnostic copy of the spec, not committed) showed the same frame in every failing run:

```
@3964 value 0.1372
   tbody (Sources table, Planned rows)    266,670 1140x96 -> 266,688 1140x96
   section (Coverage)                     265,791 1142x100 -> 265,809 1142x82
   ::after (Coverage skeleton bar)        0,0 0x0 -> 438,874 952x16
   div.bg-skeleton (Coverage bar)         438,878 952x13 -> 0,0 0x0
   th "Status" (Sources table)            391,458 217x32 -> 414,458 186x32
```

- **Shifting element:** the shimmer `::after` of a Coverage skeleton bar (`ui/skeleton.tsx`).
- **The real move is small.** The Sources rows land 18 px taller than their skeleton (a 2 px row-height miss on each row, plus the Shopify status note), then 10 px more when the host call adds Google Trends' overdue note. That pushes the Coverage skeleton down 18 + 10 px. In a passing run the same move scores 0.0041.
- **The jump.** Chrome reports the bar's shimmer pseudo-element as moving from `(0,0,0×0)` to its bar at y 874. That makes the distance fraction 874 / 1440 ≈ 0.61, so the frame scores 0.137.
- **When.** Only when Sources lands before Host and Coverage, while the Coverage skeleton is still on screen. All calls share the 2.5 s fixture delay, so the order depends on the runner. That is why the failure was flaky locally and steady on CI. Holding Host and Coverage back 700 ms makes it deterministic: 8 of 8 runs failed, at 0.143 or 0.358.

### Cause

Each hypothesis was tested in the deterministic order with CSS injected into the diagnostic copy:

| Variant | CLS |
|---|---|
| As built (shimmer box `left: -100%` + static `translate: -33.333%`, animated `transform`) | 0.143–0.358 |
| Shimmer animation off | 0.0095 |
| `::after` removed | 0.0095 |
| Skeleton fade (`opacity`/`appear`) off, shimmer kept | 0.143–0.358 (no effect) |
| `will-change: transform`; `contain: paint`; bar `translateZ(0)`; `overflow: clip` | 0.143–0.358 (no effect) |
| Shimmer box = the bar, static translate kept, animated | 0.099 |
| Shimmer box = the bar, no translate, animated | 0.0071 |
| **Same three-bar box, offset by `left: -200%`, no translate** | **0.0071 (4/4)** |

**Cause:** a static CSS `translate` on the shimmer `::after`, next to its animated `transform`. When a panel above moves the skeleton, Chrome attributes that pseudo-element's shift from the viewport origin. p1-53 (`74cd556`, DEC-203) made the sweep box cover its bar. That cut the jump at 375 but kept the static translate (`-translate-x-1/3`), so the quirk is older than `d341e64`.

**What exposed it:** p3-05 (`e45eb878`, merged as `fe15473`) removed the AliExpress "Planned" row from the Sources panel. That moved the Coverage skeleton 32 px up, into the 1440×900 window. With that row put back, the same worst-case order scores 0.007–0.008, because the bars sit below the fold.

## 2. Page-level Retry (`retry-focus.spec.ts:87`)

CI `d9b73ef` log: after Enter on the API-down Retry, "Refreshing…" was visible. Then `getByRole("button", { name: "Retry" })` resolved to **2** elements 6 times and **1** element 18 times, never 0, for 10 s. No trace artifact was uploaded.

- **Not reproduced as a failure:** 20 of 20 passes locally on `b3d082a`, and 10 of 10 on `d9b73ef`'s components at 4× CPU throttling. It passed on CI `b3d082a`.
- **The state is real.** At 10× throttling, a timeline of Retry buttons after the press showed it on 3 of 3 runs: "Refreshing…" with the Sources panel's own Retry for 250–290 ms, then "Can't reach the API".
- **Mechanism:**
  - The page becomes "Can't reach the API" only when *both* core calls (sources, host) have failed.
  - TanStack retries each call once, after about 1 s.
  - If one call fails before the other, the page sits in its normal layout with that panel's load error and Retry showing. The Backups card's Retry shows too, since its call also failed. Meanwhile the header still reads "Refreshing…" for the call still in flight.
  - On CI's runner that lasted about 3 s with 2 buttons. The test's "Refreshing…" check passed inside it, so the count never read 0.
- **Not extra fetches.** Request logs at 4× throttling show the same 4 calls at the press and the same 4 retries with and without the change.

**Change (DEC-305 c):**
- `useCoreSettling()` (`api.ts`) is true while neither core call has data and either is still in flight.
- While it holds, the host, backups, sources, coverage, Open gaps and import panels keep their skeletons instead of their own load error. These live in `summary-cards.tsx`, `sources-table.tsx`, `coverage.tsx` and `import-panel.tsx`.
- When both core calls fail, the page reads "Can't reach the API" as before. When either has data, each panel loads and fails on its own as before. A paused offline fetch isn't "in flight", so offline is unchanged.

**Test:** "page-level Retry: no panel error flashes while the other core call is still in flight".
- After the press, the host call answers 1.5 s late, so sources fails first, the order CI's runner hit.
- An in-page observer records any "Retry" button shown while the page isn't "Can't reach the API".
- With the hold stubbed off it fails 3 of 3, recording `["Backups"]`. With the hold on it passes.
- The other 13 retry-focus cases pass unchanged.
