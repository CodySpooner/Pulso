- **XR-45 (p3-03):** Retry-After and the "ban will last N seconds" wait are measured from the lookup's start, not from the answer. `lookup.py:154` takes `at = now()` once, before any call, and `:112`/`:196` add the wait to it. A 5 s answer with `Retry-After: 3` sets `retry_not_before` to start + 3 s, already 2 s past, so the next lookup calls inside the ban. Fix: take `answered = now()` after `send()` returns and give it to `_block()` (as the lifecycle uses `captured_at`); add a slow-answer test. Fix before the owner turns `ALIEXPRESS_ENABLED` on.
- **XR-46 (p3-03):** `lookup()` keeps its read transaction open across both HTTPS calls (`lookup.py:153-208`, up to 2 × 30 s), and it doesn't re-read the source before the freight call. The lifecycle commits before HTTP (DEC-099). Probe: one `idle in transaction` session during the call. Under p3-05's endpoint each lookup pins a pooled connection and a lock on `sources`, so an `ALTER TABLE sources` queues behind it. The success reset at `:188` also reads a stale count. Fix: commit after the source checks and before `send`, and `session.refresh(source)` before each call.
- **XR-47 (p3-02):** the keyword length is checked before casefolding. `KeywordIn` checks `max_length=100` (`routers/product_keywords.py:39`), then `searchable()` normalizes (`keywords.py:39-41`), and `casefold()` can grow it. Probe: `"ß" * 100` (200 after casefold) and `"ﬃ" * 34` each answer **500** `internal_error` (varchar(100) overflow). Fix: refuse `len(normalize(keyword)) > 100` in `searchable()` (a 422), with a test. imp-347 (`NoNulStr` on the same field) finished before this review did, so XR-47 stays here.
- **XR-48 (p3-06):** an approved seed holding a comma now makes every keyword GET and POST answer **500**, because `weekly_set()` raises (`google_trends/__init__.py:163`) and the API calls it on every read (`product_keywords.py:156, 174, 192`). The POST commits its decision first (`:191`), so the save succeeds while the page shows it failed. Before KW-2, only the Monday plan failed. Seed validation allows commas (`seed_approval.py:67-72`), and seed_v1 has none. Fix: refuse a comma keyword in `validate_seed_entries`, so approval fails where the owner sees it. Also have the API answer `trends.enabled: false` instead of a 500 when `weekly_set` raises, with a test.
- **XR-49 (p3-04):** an Amazon cursor whose rank is outside int64 answers **500**. `CURSOR` is `tuple[str, str, int, str]` with no bound (`routers/amazon.py:24`). Probe: ranks `10**30`, `2**63` and `-(2**63)-1` each give 500 (`NumericValueOutOfRange`). Fix: `Annotated[int, Field(ge=0, le=2**31 - 1)]` (rank is int4), like products' XR-18 cursor bound.
- **XR-50 (p3-04):** "Load more" after a new import mixes two days in one list. The shown captures are recomputed on every request, and the cursor carries no capture (`amazon.py:116-137`). Probe: page 1 at limit 2 (Oct 24: ranks 1–2); import Oct 25; page 2 → ranks 2–3 of Oct 25. Rank 2 then shows twice under the "as of Oct 24" header (`amazon-ranks.tsx:201, 210`), and one ASIN can appear twice in a `<tbody>` (duplicate React key, `key={row.asin}`). Fix: carry the shown capture (`raw_payload_id`, `parser_version`) in the cursor, or answer 409 when page 1's `lists[].captured_at` changed.
- **XR-51 (p3-04):** an old list gets no stale warning in the default view when another list is fresh. `stale` is computed on the newest day across the shown lists (`amazon.py:166-168`), and unfiltered that is every list. Probe: Home imported today, Toys 60 days ago → unfiltered `stale: false`; `?category=Toys` → `stale: true`. DEC-286 (b) rejected exactly this ("a fresh list would hide an old one").
