## The change

| Where | Before | After |
|---|---|---|
| `packages/ml/src/pulso_ml/matching/decisions.py` `membership()` | `ORDER BY listing_id, decided_at DESC, id DESC` | `ORDER BY listing_id, id DESC`; the `WHERE decided_at < t` cutoff is unchanged |
| `packages/ml/src/pulso_ml/matching/matcher.py` `manual()` | `ORDER BY decided_at DESC, id DESC` | `ORDER BY id DESC` |

Two docstrings say why. Nothing else in either file changed, so p2-25 (UX-1) should rebase over this without conflict in the service functions.

**Why `id` is the lock order (DEC-266 b).**
- Every writer inserts decision rows only after it takes the matching lock: `merge`, `split`, `accept` and `reject` call `lock()` first and `record()` after; the score pass (`matcher.py:161`) and the GTIN pass (`:312`) lock before `link()`. The lock is held until commit.
- `match_decisions.id` is an identity column with `CACHE 1`. A probe on the migrated test schema read `pg_sequence` as `(seqcache, seqincrement) = (1, 1)`. So `nextval` is handed out in call order across sessions, and a transaction that takes the lock later gets higher ids than one that committed before it.
- Within one transaction every `decided_at` is equal (`now()`), so the old order already fell back to `id DESC` there; nothing changes inside a transaction.
- Rows already written read correctly with no rewrite. History stays append-only.

**The cutoff (DEC-266 c).** It stays on `decided_at` (DEC-031). The fix changes which row wins only among rows already before the cutoff, and only where their stamps and ids disagree, which is the XR-29 race. A cutoff inside two overlapping requests sees the same rows it saw before; that window is one request long.
