### p2-04 allowlist · no bypass; XR-15 low

- **Exact host:** the host is lowercased on both sides (`:76-81`, `:230`).
- **Refused:** `http`, another port (`:8443`), and a trailing-dot host (`cdn.example.test.`).
- **Normalized:** `:0443` and a bare `:` both mean port 443. An upper-case scheme or host still matches.
- **IP literals:** `127.0.0.1` and `[::1]` pass only if they are listed.
- **Tricks that land on an unlisted host:** `%40`, `%2F@` and the fragment form `evil#@cdn` all resolve to a hostname that isn't on the list.
- **Unicode case folding:** U+212A KELVIN SIGN folds to `k`, and that is the same ASCII name urllib's IDNA encoding connects to, so it is the same host.
- **Leading spaces:** both parsers strip them.
- **Userinfo and backslash:** `https_host` takes the host after `@`, but urllib connects to the whole netloc. See XR-15.
- **`IMAGE_HOSTS` entries aren't validated:** an `https://` prefix or a `:443` suffix makes an entry match nothing. See XR-12, scenario 2.

### p2-04 validation and storage · clear

- **Order:** `check` runs inside `fetch` (`:125-136`), before `_capture` stores the response (`lifecycle.py:140-158`). A raised `ImageContentType`, `ImageTooLarge` or `ImageUndecodable` leaves `_capture` before `store_capture`, so nothing reaches `raw_payloads` or S3. The p2-04 test asserts that the only capture is robots.txt.
- **Checks:**
  - Media type (`:62-64`).
  - 5 MiB: `read(MAX_BYTES + 1)` (`:115`), then `len > MAX_BYTES` (`:66-67`).
  - 40 MP read from the header, before `load()` (`:52-57`).
  - Pillow is limited to four formats (`:53`).
  - `DecompressionBombError` maps to `ImageTooLarge` (`:70-71`). Pillow's own bomb limits (warning above about 89 MP, error above about 179 MP) sit above 40 MP.
- **No `Accept-Encoding` is sent,** so the byte cap is a cap on the decoded size.
- **Stored once:** `upsert` writes `storage_key` and `phash` once (`:153-158`).
- **Non-2xx bodies** (a 404 page, a 503, robots.txt) are stored without validation, up to 5 MiB + 1 byte each. That is the framework's norm for evidence, and they're never parsed, because `ResponseFailed` comes first.

### p2-04 pHash · clear

- **The transform:** `_DCT @ X @ _DCT.T` is an unnormalized 2-D DCT-II. Scale doesn't matter to a median threshold.
- **The bits:**
  - It takes the top-left 8×8 block, DC included, and sets the bits above the median.
  - `packbits` fills them row-major, MSB first: the same bit order as `imagehash.phash`.
- **Signed value:** `value − 2^64 if value >> 63` maps [0, 2^64) onto [−2^63, 2^63) (`:19`).
- **Similarity:** `similarity` masks the XOR to 64 bits before `bit_count`, so the signs don't matter (`:24`). The BIGINT round-trip test passes.
- **Notes for M-3 (not defects):** `convert("L")` drops alpha, so a transparent background is hashed as the RGB underneath it, often black. EXIF orientation isn't applied. `imagehash` does the same.

### p2-04 run evidence · backoff clear; XR-12 low

- **Backoff** (`:206-227`):
  - It counts targets that are `failed`, or not `success` with a capture.
  - `captured_at` is always set: `execute_run` sets it when it creates the pending rows and again when they finish (`lifecycle.py:272-283, 333`). So `last` is never None.
  - Deferred, run-stopped and robots-skipped targets are `partial` with no capture, so they carry no penalty (probe and the p2-04 test).
  - Blocked images are `partial` with a capture, so they back off.
- **Empty plan** (`:255-263`): see XR-12.

### p2-04 migration 0006 and wiring · clear

- **Upgrade:** it inserts one row. `sources.id` has `autoincrement=False`, and 0001 and 0002 also seed explicit ids.
- **Downgrade:** it deletes only that row. Every foreign key to `sources` is NO ACTION, so any run, capture, event, listing or mapping refuses the delete (probe).

## Findings

### XR-11 · medium · p2-04 · a robots.txt answering 200 resets the block count every run, so image blocks never disable the source

- **Where:**
  - `packages/sources/src/pulso_sources/framework/lifecycle.py:163-169`: any live response outside `BLOCK_STATUSES` sets `consecutive_block_count = 0`.
  - `lifecycle.py:298-299`: the first block stops the run.
  - `packages/sources/src/pulso_sources/listing_images/__init__.py:160-161`: robots.txt goes through the same `_capture`.
  - `listing_images/__init__.py:244`: robots targets are planned before every image.
  - `packages/sources/tests/listing_images/test_listing_images.py:296`: the block test reaches the threshold only by switching robots.txt itself to the block status.
  - `docs/DATA_SOURCES.md:176` and DEC-240 (d) (`docs/DECISIONS.md:1953`): both promise the disable after 5 consecutive blocks.
- **Defect:**
  - Every run asks for robots.txt first. A 200 resets the count to 0, and the first blocked image takes it to 1 and stops the run.
  - While robots.txt answers 200, the count never passes 1, so `collector_block_threshold` (5) is unreachable for image blocks.
  - DEC-240 (d) records the reset, but not that it makes the rule unreachable. imp-200 defers the question until after enabling.
- **Failure scenario:**
  1. The owner enables the source with `IMAGE_HOSTS=cdn.example.com`. The CDN starts answering 403 to PulsoBot's image requests, but still serves robots.txt with 200.
  2. Each daily run: robots.txt 200 sets the count to 0. The first image 403 sets it to 1, and the run stops `partial` with `http_403`.
  3. In the probe, 5 runs with the threshold set to 2 left the count at 1 after each run. The source stayed enabled, with 0 `source_events` rows and 10 requests.
  4. Data Health shows Partial, never Blocked. The adapter keeps sending 2 requests a day to a host that refuses it, with no end. Neither SPEC §4.2 ("If a source blocks us, disable the adapter and log it") nor DEC-033's auto-disable holds.
  5. Combined with XR-12, once the host's few pending images are all in backoff, the quiet days even read Healthy.
- **Impact:** a compliance gap once the source is enabled. It isn't active now: the source is disabled and the allowlist is empty.
- **Fix** (smallest first):
  1. Don't let a robots.txt response reset the count. Add a `Request` field such as `resets_blocks: bool = True` (`framework/__init__.py:21-27`) and set it to False on the robots request (`listing_images/__init__.py:161`). When it is False, `_capture` keeps the count on an answer that isn't a block. A robots.txt answering 403, 429 or 430 still counts as a block.
  2. Or count consecutive blocks per host from run evidence, as the backoff already does, and disable when one host blocks N runs in a row.
- **Test:** run `test_consecutive_blocks_disable_once_and_stop_the_run` with robots.txt answering 200 throughout. After `threshold` runs, there is exactly one disable event and `enabled = false`.
- **Also:** `shopify_stores` sends robots.txt through the same `_capture` before each store's JSON (`shopify_stores/__init__.py:154-162`), with a 24 h cache. It may share this defect whenever that cache has expired. This review didn't check it. Option 1 would cover both adapters.

### XR-12 · low · p2-04 · a quiet day records `success` while every due image is failing or unlisted

- **Where:**
  - `listing_images/__init__.py:238-241`: unlisted and backed-off images are only counted.
  - `listing_images/__init__.py:247-254`: the log line.
  - `listing_images/__init__.py:255-263`: the plan-capture target, which ends `success`.
  - `lifecycle.py:335-342`: the run status.
  - DEC-096's display states (`docs/DECISIONS.md:1124`): a last run of `success` shows Healthy.
  - DEC-240 (i) (`:1958`).
- **Defect:** the counts that would show the trouble (`unlisted_host`, `backoff`) live only in the plan capture and a log line. The run reads `success`, `complete` and a null `error_code`.
- **Failure scenario:**
  1. **Backoff:** a host answers 404, or a body that isn't an image, for every image. In the probe, one such image over 10 daily runs gave partial, partial, success, partial, success, success, success, partial, success, success. At the 30-day cap, the source reads Healthy on 29 days out of 30.
  2. **Allowlist typo:** `IMAGE_HOSTS=https://cdn.shopify.com` (or `cdn.shopify.com:443`, or an empty value) leaves every image unlisted. In the probe, the run read `success` every day with 0 requests. Data Health shows Healthy, and M-3 then finds no pHash anywhere (weight 0).
- **Impact:** diagnostics only. Nothing is stored wrong. It makes XR-11 worse until XR-11 is fixed.
- **Fix:**
  1. When `pending > 0` and every pending image is unlisted, record the plan target as `partial`, with a named `error_code` such as `NoListedHost`. This is always a misconfiguration, never noise.
  2. Validate `IMAGE_HOSTS` entries in `Settings` as bare lowercase DNS names: no scheme, port or `@`.
  3. Show the `backoff` count where Data Health shows the run (the run drawer). Let imp-198 decide whether a quiet day with images in backoff still reads healthy.
- **Test:** a mistyped `IMAGE_HOSTS` gives a `partial` run with `NoListedHost`. Nothing pending still gives `success`.

### XR-13 · low · p2-04 · one host's Crawl-delay paces every host, and a delay past the budget stops the run for all of them

- **Where:**
  - `listing_images/__init__.py:96-100`: an in-line sleep, and `RunDeferred` when the wait would cross the deadline.
  - `listing_images/__init__.py:244-246`: the round-robin runs over one sequential target list.
  - `lifecycle.py:328-330`: `RunDeferred` stops the run.
  - DEC-240 (e) (`docs/DECISIONS.md:1954`): "one host's spacing never idles another".
- **Defect:**
  - Targets run one after another, and `fetch` sleeps in-line, so each round takes as long as its slowest host's spacing.
  - A wait that would cross the deadline raises `RunDeferred`. That stops every remaining target, other hosts' images included.
- **Failure scenario:**
  1. Hosts A and B are listed. A's robots.txt says `Crawl-delay: 3000` (50 min, past the 45 min budget).
  2. In the probe, B's image was never requested, and the run read `partial` with `RunDeferred` / `wall_time_budget`. That repeats every day, so B is starved.
  3. A smaller case: with `Crawl-delay: 60` on A, each round takes at least 60 s, so B gets at most about 45 images a run instead of 1,350.
- **Impact:** throughput only, and it fails closed: it can only mean fewer requests, never more. The run's error names the budget, not the host.
- **Fix:** in `image_requests` (`:173-179`), return without a request when the host's next slot `_next_host[host]` is past `self.deadline`. The target ends `partial` with no capture and no penalty, and the other hosts carry on. Optionally, pick the next target by the soonest allowed time instead of a fixed `zip_longest`.
- **Test:** host A has a Crawl-delay at or above the budget, and every one of host B's images is still fetched.

### XR-14 · low · p2-04 (shared with shopify_stores) · a fractional Crawl-delay is ignored, and `Request-rate: 0/n` fails robots with ZeroDivisionError

- **Where:**
  - `listing_images/__init__.py:166-169`, and the same code in `shopify_stores/__init__.py:167-170`.
  - Python's `urllib.robotparser` keeps a Crawl-delay only when the value passes `isdigit()`.
- **Failure scenario:**
  1. A robots.txt with `Crawl-delay: 10.5` makes `crawl_delay()` return None, so the spacing stays at 2 s. In the probe, the gaps were 2.0, 2.0 and 2.0 s: 5× faster than the host asked. DEC-240 (e) and `docs/DATA_SOURCES.md:175` both say Crawl-delay is honoured.
  2. `Request-rate: 0/1` makes `rate.seconds / rate.requests` raise ZeroDivisionError. The robots target ends `partial`, the host is skipped (it fails closed), and the `error_code` reads `ZeroDivisionError`.
- **Impact:**
  - The first case is less polite than the host asked, but only for non-integer delays above the 2 s floor. Crawl-delay isn't part of RFC 9309, so the gap is small.
  - The second case fails closed.
- **Fix:** one helper shared by both adapters.
  - Read the `Crawl-delay` values from the robots body as floats, keeping only finite, non-negative ones. Use the largest in the file, so it can only slow the crawl.
  - Treat `Request-rate` with 0 requests as a named robots refusal.
- **Test:** with `Crawl-delay: 10.5`, every gap is at least 10.5 s.

### XR-15 · low · p2-04 · the allowlist reads the host after `@`, but urllib connects to the whole netloc

- **Where:**
  - `listing_images/__init__.py:76-81`: `urlsplit(url).hostname`.
  - `listing_images/__init__.py:104-110`: `URLRequest(url)`, whose `.host` is the netloc, userinfo included.
  - `listing_images/__init__.py:236-243`: planning and the per-host budget are keyed by the parsed host.
- **Defect:** the check and the connection parse the URL differently.
- **Failure scenario:**
  1. A catalog or CSV row stores `https://x@cdn.shopify.com/a.jpg`, or `https://x\@cdn.shopify.com/a.jpg`.
  2. `https_host` returns `cdn.shopify.com`, which is listed, so the image is planned under that host's robots and budget.
  3. urllib connects to the literal name `x@cdn.shopify.com`. In the probe, `Request.host` was `'evil.test@cdn.example.test'`.
  4. That sends a DNS lookup for a name nobody listed, under the listed host's parent domain. TLS name checking then fails, so the request ends as `URLError` → `ConnectionError`, and the image fails and backs off.
- **Impact:** one odd DNS lookup and one failed image. The connect name always ends in `@<listed host>`, so no other host gets an HTTP request. This is defence in depth.
- **Fix:**
  - In `https_host`, return None when `parts.username` or `parts.password` is set, or when the netloc contains `\`. Or compare `parts.netloc.lower()` against `{host, host + ":443"}`.
  - Optionally, validate `IMAGE_HOSTS` entries (see XR-12, fix 2), rejecting IP literals too.
- **Test:** the userinfo and backslash forms count as unlisted.
